## 1. 优雅停机（Graceful Shutdown）

**问题**：默认 `spring.shutdown=immediate` 在收到 SIGTERM 时立即关闭 WebServer，会切断在途的支付/结算/退款请求，造成资损或状态不一致。

**方案**：
- `application.yml` 设 `server.shutdown: graceful`，Spring 停止接收新请求并等待在途请求完成。
- `spring.lifecycle.timeout-per-shutdown-phase: 30s`（基础）/ `45s`（prod）为单阶段宽限。
- k8s `terminationGracePeriodSeconds: 60s` 大于 45s，留出余量。
- Pod `preStop` 先 `sleep 15s`：让 Ingress/Service 端点摘除与在途连接排空，**之后**才发 SIGTERM 进入 Spring 优雅停机，避免瞬时 5xx。

**序列**（滚动更新单 pod 下线）：
```
kubelet 触发删除 → Endpoint 摘除（~数秒）→ preStop sleep 15s（排空在途）→
SIGTERM → Spring graceful shutdown（最长 45s，等待支付/结算在途完成）→ 进程退出 →
terminationGracePeriod 60s 兜底强杀
```

## 2. 探针设计（复用 F-12.5 / T01 零依赖 `/actuator/health`）

`ObservabilityController` 提供零依赖 `/actuator/health`，同时探测 MySQL/Redis/ES/RocketMQ/OSS/SMS。本模块强化其 HTTP 语义：

| 场景 | overall status | HTTP | k8s 行为 |
|---|---|---|---|
| 全依赖正常 | UP | 200 | 正常服务 |
| 次要依赖降级（如 ES 不可达） | DEGRADED | 200 | **不摘流**，核心交易链路不受影响 |
| 核心依赖（MySQL）不可用 | DOWN | **503** | readiness 摘流 + liveness 重启 |

三类探针：
- `startupProbe`：前 150s 保护慢启动（JVM/DB 初始化），失败不计入 liveness。
- `readinessProbe`：20s 后每 10s 探一次；MySQL 503 即摘流，保证流量只进健康实例。
- `livenessProbe`：60s 后每 15s 探一次；长时间无响应重启。

> 与现有 Dockerfile `HEALTHCHECK` 同源：`curl -fsS http://localhost:8080/actuator/health`（容器内探活）。

## 3. 弹性伸缩（HPA）

`hpa.yaml`（autoscaling/v2）：
- `minReplicas: 2` / `maxReplicas: 10`，伸缩目标 `Deployment/idlefish-backend`。
- **主指标** CPU 利用率 70%（依赖 metrics-server，开箱即用）。
- **可选** 入口 QPS 指标（注释示例）：需 prometheus-adapter 将 `/actuator/prometheus` 暴露的计数器映射为 `idlefish_backend_qps_per_pod`，目标单 pod 200 QPS。
- 行为：扩容即时（单次最多翻倍 / +4 pod，30s 窗口）；缩容冷静 300s，单次 -1 pod/60s，抑制抖动。

> 注：HPA 接管副本数，因此 ArgoCD `ignoreDifferences` 显式忽略 `/spec/replicas`，避免 Git 声明值与 HPA 实际值互相覆盖。

## 4. GitOps（Argo CD）

`argocd-application.yaml` 以 Git 仓库（`path: deploy/k8s`，`targetRevision: V1.0.4`）为唯一事实源：
- `syncPolicy.automated`：`prune`（清理删除资源）+ `selfHeal`（纠偏集群漂移）。
- `retry` 指数退避（最多 3 次）。
- `ignoreDifferences`：忽略 Deployment 副本数（交 HPA 管理）。
- 部署前：改 `repoURL` 为实际仓库、在 ArgoCD 配置仓库凭据、确保 `idlefish` namespace 可创建（`CreateNamespace=true`）。

## 5. CI / CD（`.github/workflows/ci.yml`）

三段式：
1. **build-test**：`setup-java` 缓存 Maven → `mvn -B -P!micrometer clean verify` 全量测试；随后以非 strict 运行 `scripts/dependency-governance.sh` 作为趋势观察。
2. **image**（仅 tag/main/V1.0.4 push）：Buildx 构建镜像 → 推送私有仓库（多 tag：版本 + latest）→ Trivy 高危漏洞扫描（SARIF 上报，默认不阻断）。
3. **sync**（tag push 或手动 dispatch）：ArgoCD CLI `app sync --prune` 触发 GitOps 同步。

> CI 使用在线 Maven（GitHub runner 联网），与本地沙箱"离线只读仓库"构建解耦；二者均受 `dependencyManagement`/`pluginManagement` 收敛保护（见 T08）。

## 6. 部署步骤

```bash
# 1) 准备密钥（务必替换占位）
kubectl create secret generic idlefish-backend --namespace idlefish \
  --from-literal=JWT_SECRET='<32+字节随机串>' --from-literal=IDLEFISH_PAY_APIV3_KEY='...' ...

# 2) 一键交付（kubectl）
kubectl apply -k idlefish-backend/deploy/k8s

# 3) 或 GitOps（Argo CD）
kubectl apply -f idlefish-backend/deploy/k8s/argocd-application.yaml

# 4) 观测
kubectl -n idlefish get deploy,po,hpa,pdb,svc
kubectl -n idlefish describe hpa idlefish-backend
curl -fsS http://<pod-ip>:8080/actuator/health
```

## 8. 已知限制与后续

- 当前未启用 QPS 自定义指标（需 prometheus-adapter + 指标规则），HPA 仅 CPU 驱动；CPU 对"突发流量"响应滞后于 QPS，强烈建议生产补齐 QPS 指标。
- `secret.yaml` 为占位模板，真实密钥须经 Secret 管理（Vault / KMS / SealedSecrets）注入，**禁止明文入库**。
- 镜像 tag 在 CI 中以 `sha8` / 语义化 tag 推送；生产建议锁定 digest 防漂移。
- 沙箱无集群，未做真实 `kubectl apply`；上线前需在预发集群完成端到端验证（探针 503 摘流、滚动零停机、HPA 触发）。
