## 1. 规划原则与优先级判定

- **横切基建优先**：被多个功能依赖的组件（真实登录、通知中心、测试/CI、安全基座）必须前置，否则后续功能会反复返工。
- **真实上线为准出**：所有功能以"真实后端（非 Mock）联调通过"为验收门槛，禁止以 Mock 演示替代（延续 `RK-3` 约定）。
- **优先级分级**：
  - **P0（必须先做）**：阻塞生产上线或影响全站触达/安全的横向基建。
  - **P1（核心体验）**：缺失即交易/信任闭环不完整的功能。
  - **P2（增长/运营）**：提升留存与 GMV 的扩展能力。
  - **P3（长期/规模化）**：架构演进与合规，非短期阻塞项。
- **单人项目约束**：当前仅 1 名开发者，排期为相对周（W），增派人手可并行压缩；每个阶段结束须在本机/连接器对真实后端联调（延续 `scripts/verify-backend.sh`）。

```

        │
        ▼
[阶段四 · 增长运营]

        │
        ▼
[阶段五 · 规模化]
```

**先后顺序要点**：
1. **F-02 通知中心是枢纽**：F-05/F-06/F-07/F-10 均依赖它做触达，必须先建。
2. **F-01 真实登录是小程序上生产的硬前置**：不接 code2session，小程序无法获真实 openid，支付 JSAPI 与用户体系均无法闭环。
3. **后端重（结算/退款/提现）已就绪，瓶颈在前端**：F-07/F-08 主要是前端补页 + 联调，性价比高，紧随基建之后。
4. **F-13 真实凭据验证贯穿始终**：每个 Real 实现（支付/登录/OSS/ES/MQ/物流/内容安全）接入凭据后需端到端验证，是公测前的统一闸门。

## 4. 分阶段迭代计划

### 阶段一 · 生产就绪基建（相对周 W1–W3，P0）
- **目标范围**：把"可演示"升级为"可上线"，交付被后续所有功能依赖的横向基建 + 发布闸门骨架。
- **交付内容**：
  1. **F-01 真实微信登录**：新增 `RealUserLoginServiceImpl`（`code2session` 换 openid → 绑定/注册用户 → 签发 JWT），沿用 `idlefish.login.mock` 开关；`AuthController.login` 支持 `jsCode` 入参。
  2. **F-02 通知中心**：`t_notification(id,user_id,type,biz_id,title,content,read,ctime)` + `NotificationService`（发信/已读/列表/未读计数）+ `GET /api/notify/*`；定义统一领域事件（订单/支付/退款/审核/风控）。
  3. **F-03 测试与 CI**：核心链路单测（结算幂等、退款状态机、乐观锁 CAS 冲突、金额换算）+ `mvn test` 跑通（解决 surefire 离线问题或固化 `SmokeRunner` 路径）+ 简易 CI 配置。
  4. **F-04 安全加固收尾**：JWT 改 httpOnly Cookie（PC/小程序分别处理）、密钥/端口/环境配置外置（`application.yml` → 环境变量）、`t_*` 逻辑删除列评估、`GlobalExceptionHandler` 补全异常类型、API 限流骨架（`@RateLimiter`/Bucket4j 或网关层）。
- **实现要点**：通知中心用 Spring `ApplicationEvent` 解耦，所有状态变更统一发事件；真实登录与 Mock 登录共存，默认 Mock 保证沙箱可跑。
- **验收标准**：小程序可用真实微信登录；系统事件可经通知中心触达（至少订单/支付/退款事件有站内信）；`mvn test` 绿；密钥不落地明文；限流对单 IP 生效。

### 阶段二 · 信任与履约补全（相对周 W4–W6，P1）
- **目标范围**：补齐买卖双方信任闭环与履约触达，让"下单后"的全流程有反馈、有评价、有纠纷出口。
- **交付内容**：
  1. **F-05 事件通知闭环**：`RemindShipHandler`/`ConfirmReceiveHandler`/`CloseOrderHandler` 及支付/退款/审核状态变更统一经 F-02 通知中心触达买卖双方；前端通知红点/未读。
  2. **F-06 评价与信用体系**：`t_review(id,order_no,reviewer_id,target_user_id,score,content,ctime)` + 买卖互评端点 + 完成后写回 `User.creditScore`（如加权均值/好评率映射）+ `SellerVO` 信用分动态展示。
  3. **F-07 退款/纠纷前端闭环**：小程序 `refund` 页（申请/进度/取消）+ PC `退款管理` 视图（列表/同意/拒绝/平台介入）+ 轻量申诉（纠纷标记流转到后台）。
  4. **F-08 钱包/提现前端**：小程序 `withdraw`/`wallet` 页（可用余额、提现申请、记录）+ PC `提现审核` + `对账` 视图（与 `TradeScheduler.reconcileDaily` 对账报告联动）。
- **实现要点**：评价与订单强绑定（仅 `completed` 订单可评，双向幂等）；信用分变更走事务 + 审计；纠纷以退款单状态扩展（`platform` 态）实现，不另起大系统。
- **验收标准**：支付/发货/确认/退款均产生对应站内信；完成订单双方可互评且信用分更新；小程序与 PC 退款、提现、对账全链路真实后端跑通。

### 阶段三 · 小程序端到端体验闭环（相对周 W7–W8，P1）
- **目标范围**：小程序补齐交易相关全部页面，达到可真机使用的完整度。
- **交付内容**：
  1. **F-09 小程序缺失页**：`refund`（已交付）+ `evaluate`（已交付）+ `withdraw`（已交付）三个页面（含"我的"菜单接入）；`notification`/`bargain` 两个页面待交付；IM 实时接线（`chat` 页 `wx.connectSocket` 对接已就绪的 `ImWebSocketHandler`）。
  2. **支付回流与登录态打磨**：订单详情/列表 `setInterval` 轮询支付结果 + 30 分钟倒计时；`request.js` 401 分支接 `refreshToken` 无感续期。
- **实现要点**：优先复用已存在的后端端点（退款/评价/通知/提现/砍价），前端以"补页 + 接真实 API"为主，避免后端返工；IM 服务端已就绪，纯前端接线。
- **验收标准**：小程序在真实后端下完成 登录→浏览→下单→支付→发货→确认→评价→提现 全链路；IM 消息实时收发；支付超时可见、登录过期无感续期。

### 阶段四 · 增长与运营（相对周 W9–W11，P2）
- **目标范围**：提升转化与留存，强化运营决策能力。
- **交付内容**：
  1. **F-10 优惠券/营销**：`t_coupon`/`t_user_coupon`（满减/折扣/新人券）+ 领取/核销 + 下单抵扣 + 发放经 F-02 通知。
  2. **F-11 数据看板深化**：GMV/成交量趋势、转化漏斗（发布→下单→支付）、品类分布、用户留存（DAU/留存率）、风控命中概览。
  3. **F-12 客服工单/纠纷申诉正式化**：在 IM `cs-entry` 基础上建立工单（分配/状态/时效 SLA），与退款纠纷联通。
- **实现要点**：券与订单金额计算须复用"分"单位契约（防 RK-1 资损回潮）；看板数据来自既有 `t_order`/`t_item`/`t_user` 聚合，避免新建埋点体系。
- **验收标准**：券可领可用可抵扣；看板多维指标可筛选；工单可分配可闭环。

### 阶段五 · 规模化与合规（相对周 W12+，P3）
- **目标范围**：支撑业务规模增长与合规要求。
- **交付内容**：
  1. **F-13 真实凭据端到端验证**（发布闸门）：支付证书/APIv3 密钥、OSS、ES 集群、RocketMQ、物流 key、内容安全 key、微信登录全部接入，逐组件端到端验证并关闭 fail-closed。
  2. **F-14 风控升级**：规则引擎平台化（规则可配置）、设备指纹关系图谱、引入 ML 模型识别欺诈。
  3. **F-15 规模化与合规**：分库分表/多租户评估、实名认证与反洗钱合规、多端（H5/APP）适配、国际化（多语言/多币种）。
- **实现要点**：F-13 应在公测前作为统一闸门完成；F-14/F-15 为非阻塞长期项，按业务节奏启动。
- **验收标准**：七大组件真实模式全部端到端通过；风控可运营配置；具备基础合规能力与多端出口。

## 5. 跨阶段工作流（两条贯穿线）

- **上线准出线（F-13）**：与阶段一~三并行。每接入一个真实渠道（登录→支付→OSS→ES→MQ→物流→内容安全），立即在本机/连接器对真实后端做端到端验证，验证通过才允许该渠道关闭 Mock。公测前七大组件必须全绿。
- **测试/CI 线（F-03）**：阶段一开始建骨架，每个后续阶段新增功能须同步补单测/集成测试，保持 `mvn test` 绿。严禁以 Mock 演示替代真实后端验收（延续 `RK-3`/`scripts/verify-backend.sh`）。
