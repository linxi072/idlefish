## 一、背景与问题

**已具备**
- 支付回调：**恒定验签** + **条件更新** + **affected 行网关**三重防重；金额不符回调被拒。
- 提现出款：未配置凭据时**硬网关拦截**，绝不出款。
- 金额全链路统一「分」；`pay-callback-sim.js` 支持 `--mock/--live/--v3/--v3-sign`。

**待解决问题**
1. **未验证规模化正确性**：幂等网关在并发/重试风暴下的表现仅有单点验证，缺少高并发证据；一旦被击穿即造成**资损**（重复入账/重复出款）。
2. **对账靠人工**：分账结果、资金流水、微信账单之间缺少自动核对，差异发现滞后（T+1 甚至更晚）。
3. **压测场景缺失**：无针对「回调风暴」「重复回调」「部分失败重试」的标准化压测用例与基线。
4. **失败可观测但不可自愈**：分账失败已落库，但缺少自动重试编排与人工兜底队列。

**用户痛点**：财务需手工比对账单，发现差异时已过账；大促峰值下若重复入账，平台需承担赔付与信任损失。

---

## 二、目标与非目标

**目标（可度量）**
- G1：在目标峰值 QPS 下，**重复入账/重复出款 = 0**（压测 + 混沌注入验证）。
- G2：日终对账**自动化**，差异（金额/笔数/状态）当日发现并告警，差异处理时长 ≤ 4 小时。
- G3：建立资金链路压测**基线用例集**（含回调风暴、重复回调、乱序回调、金额篡改），纳入 CI/发版门禁。
- G4：分账失败支持**自动重试（带退避）** + 人工兜底队列，重试成功率可量化。

**非目标**
- 不改变资金链路业务规则与接口契约（仅加固验证与自动化）。
- 不引入新的支付渠道。
- 不做容量规划本身（提供数据供容量决策）。

## 四、需求清单（EARS）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| REQ-01 | Ubiquitous | 系统应**始终**保证同一支付回调在任意并发下仅产生一条入账流水 |
| REQ-02 | Unwanted | 若同一提现申请被重复提交或重试，系统应仅出款一次（affected 行网关 + 唯一约束兜底） |
| REQ-03 | Event-driven | 当回调**乱序**到达（晚到的成功回调晚于关单）时，系统应拒绝入账并保持订单终态一致 |
| REQ-04 | Unwanted | 若回调金额与订单金额不一致，系统应拒绝入账并触发资损告警 |
| REQ-05 | Event-driven | 当分账失败被记录时，系统应按退避策略自动重试，重试 N 次仍失败则进入人工兜底队列 |
| REQ-06 | Event-driven | 当到达日终对账时间点时，系统应自动比对平台流水、资金流水与微信账单（笔数/金额/状态） |
| REQ-07 | Unwanted | 若对账发现差异，系统应立即生成差异记录并触发告警，差异明细需可下钻至订单与流水 |
| REQ-08 | Ubiquitous | 系统应**始终**以「分」为单位记录与比对金额，禁止浮点金额参与对账 |
| REQ-09 | Event-driven | 当执行压测基线用例集时，系统应输出幂等命中率、失败率、P99 与瓶颈指标报告 |
| REQ-10 | Optional | 若启用混沌模式，应可注入回调重复、延迟、乱序与下游超时，验证系统不产生资损 |

## 五、流程说明

**压测与混沌验证流程**
```
定义基线场景（正常/重复/乱序/篡改金额/下游超时）
  → 脚本并发投递（pay-callback-sim 扩展 --stress/--chaos）
  → 校验：流水唯一性、订单终态、金额一致、无死锁
  → 产出报告（幂等命中率、QPS、P99、错误分布、瓶颈）
  → 不达标则回归修复并重跑
```

**日终对账流程**
```
T+1 定时触发 → 拉取微信账单 vs 平台资金流水
  → 三方比对（笔数 / 金额 / 状态）
     ├─ 一致：归档对账结果，标记「已核对」
     └─ 差异：生成差异记录 → 告警 → 人工/自动处理 → 闭环归档
```

**分账失败自愈流程**
```
分账失败落库 → 退避重试（1m/5m/30m/2h/6h）
  → 成功：更新状态，闭环
  → 仍失败：进入人工兜底队列 → 运营处理 → 记录原因（对账可追溯）
```

## 六、交互说明

- **PC 后台（资金财务页扩展）**：
  - 「对账中心」Tab：每日对账结果列表（日期/笔数/金额/差异数/状态）、差异明细下钻至订单与流水。
  - 「分账失败队列」：失败单列表、重试次数、失败原因、人工重试/强制关闭操作。
  - 「压测报告」：展示最近一次资金链路压测结果（只读摘要）。
- **告警**：对账差异、资损风险（重复流水）、分账失败堆积 → 按 ITER-T01 告警分级触达（资损为 P0）。
- **CLI**：`scripts/pay-callback-sim.js --stress`（压测）、`--chaos`（混沌注入）；报告输出到 `reports/`。

## 七、数据口径与指标

| 指标 | 口径 | 目标 |
|---|---|---|
| 重复入账数 | 同订单入账流水 > 1 的订单数 | **0** |
| 重复出款数 | 同提现单出款 > 1 | **0** |
| 幂等命中率 | 被正确去重回调 / 重复回调总数 | 100% |
| 对账差异率 | 差异笔数 / 总笔数 | < 0.1%，且当日闭环 |
| 对账自动化覆盖 | 自动核对天数 / 运营天数 | 100% |
| 分账自动重试成功率 | 重试成功 / 进入重试总数 | ≥ 80% |
| 差异处理时长 | 发现 → 闭环 | ≤ 4 小时 |
| 峰值承载 | 压测得出的安全 QPS | 输出基线数据 |

## 八、边界场景与异常状态

1. 微信账单延迟生成（T+1 未出账）→ 对账任务需重试拉取，标记「待账单」。
2. 退款与分账交叉（已分账后退款）→ 需处理分账回退。
3. 压测产生脏数据污染生产/准生产库 → 压测必须使用独立环境或影子表，且数据可清理。
4. 下游（微信）限流导致重试风暴 → 需熔断与退避上限。
5. 金额精度：分账比例计算产生余数 → 需明确余数归属规则。
6. 对账任务本身失败/超时 → 需任务级告警与重跑能力。

---

## 九、权限与合规

- 对账差异处理、分账强制关闭等**高危操作**需二次确认 + RBAC 控制 + 操作留痕（谁/何时/原因）。
- 压测环境禁止使用真实资金与真实商户号出款（除非受控小额白名单）。
- 资金流水与账单数据属财务敏感数据，导出需审批，导出文件脱敏。
- 所有金额以「分」存储与计算，展示层再转元。

## 十、验收标准（可勾选）

- [ ] `--stress` 压测下重复入账 = 0、重复出款 = 0（REQ-01/02）。
- [ ] 乱序回调（晚到成功回调）不破坏订单终态（REQ-03）。
- [ ] 金额篡改回调被拒并触发资损告警（REQ-04）。
- [ ] 分账失败按退避自动重试，超次数进入人工兜底队列（REQ-05）。
- [ ] 日终对账自动执行，覆盖笔数/金额/状态三方比对（REQ-06）。
- [ ] 人为制造差异可生成差异记录、告警并可下钻（REQ-07）。
- [ ] 全链路金额以「分」比对，无浮点误差（REQ-08）。
- [ ] 压测报告输出幂等命中率/P99/瓶颈（REQ-09）。
- [ ] 混沌模式可注入重复/延迟/乱序/超时且不产生资损（REQ-10）。
- [ ] 高危操作均需二次确认并留痕。

## 十一、依赖与风险

| 类型 | 说明 | 应对 |
|---|---|---|
| 依赖 | ITER-F01 真机验收完成（真实回调与账单可获取） | 串行：F01 → T02 |
| 依赖 | ITER-T01 告警通道（资损/差异告警复用） | 复用 T01 分级告警，避免烟囱 |
| 依赖 | 准生产/压测独立环境与 MySQL | 影子表或独立库，压测后清理 |
| 风险 | 压测打爆真实商户号额度或被微信风控 | 使用小额/沙箱金额，设 QPS 上限与熔断 |
| 风险 | 对账自动修复误操作造成二次资损 | 对账只**发现与告警**，修复动作默认人工确认 |
| 风险 | 离线环境无法跑集成压测 | 纯逻辑幂等用 Mockito 单测覆盖，压测留本机/CI |
