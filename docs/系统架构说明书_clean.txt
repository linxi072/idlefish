1. 项目背景与目标
1.1 背景
闲置物品交易已从"低价甩卖"演变为兼具 性价比消费、环保循环、兴趣社交 的生活方式。参考闲鱼的成熟范式，本产品以微信小程序为载体，构建 C2C 二手交易闭环 ：用户可零门槛发布闲置、通过搜索与推荐发现商品、依托即时通讯议价、通过担保交易完成支付与收货。
1.2 产品定位
一句话定位： 面向大众的 C2C 闲置交易平台，用"轻发布 + 强信任 + 兴趣社区"降低二手交易决策成本。
与竞品的差异化取舍：

2. 用户故事（EARS 表述）
2.1 发布
编号
 | 类型
 | 需求描述
 |
US-P-01
 | Ubiquitous
 | 系统应始终允许已完成微信授权登录的用户进入商品发布流程。
 |
US-P-02
 | Event-driven
 | 当用户上传商品图片时，系统应在 3 秒内返回 AI 识别结果，并预填类目、成色、标题与描述草稿。
 |
US-P-03
 | Unwanted
 | 若图片内容命中违禁品库或涉政涉黄模型，则系统应拦截发布并提示具体违规原因与申诉入口。
 |
US-P-04
 | State-driven
 | 当商品处于"草稿"状态时，系统应保留最多 30 天并支持继续编辑。
 |
US-P-05
 | Optional
 | 在用户开启"包邮"选项时，系统应将运费字段置灰并在商品详情页展示"包邮"标签。
 |
2.2 浏览与搜索
编号
 | 类型
 | 需求描述
 |
US-B-01
 | Ubiquitous
 | 系统应始终在首页展示基于用户兴趣的个性化商品推荐流（双列瀑布流）。
 |
US-B-02
 | Event-driven
 | 当用户在搜索框输入关键词并提交时，系统应在 500ms 内返回结果列表，并支持按价格、成色、距离、发布时间排序与筛选。
 |
US-B-03
 | Unwanted
 | 若搜索结果为空，则系统应展示相近推荐与"订阅此类商品到货提醒"入口。
 |
US-B-04
 | State-driven
 | 当商品状态为"已售出"时，系统应在列表页置灰展示并禁止进入下单流程。
 |
2.3 交易
编号
 | 类型
 | 需求描述
 |
US-T-01
 | Ubiquitous
 | 系统应始终采用担保交易模式：买家支付后资金由平台（或持牌三方）托管。
 |
US-T-02
 | Event-driven
 | 当买家提交订单并完成支付时，系统应生成待发货订单并通知卖家。
 |
US-T-03
 | Unwanted
 | 若卖家在支付后 72 小时内未发货，则系统应自动触发超时提醒，并在第 5 天自动关闭订单全额退款。
 |
US-T-04
 | State-driven
 | 当订单处于"已发货"状态时，系统应展示物流轨迹，并在买家确认收货或 10 天自动确认后结算给卖家。
 |
US-T-05
 | Event-driven
 | 当买家发起"仅退款/退货退款"申请时，系统应进入协商流程，卖家 48 小时未响应则自动同意。
 |
US-T-06
 | Optional
 | 在双方同意的前提下，系统应支持"平台验货担保"增值服务。
 |
2.4 即时通讯与社区
编号
 | 类型
 | 需求描述
 |
US-I-01
 | Ubiquitous
 | 系统应始终在商品详情页提供"我想要"入口，直达与卖家的会话。
 |
US-I-02
 | Event-driven
 | 当买家在会话中发起议价时，系统应生成议价卡片，卖家确认后自动同步更新订单金额。

US-C-01
 | Event-driven

4. 核心业务流程
4.1 买家主流程
[进入小程序] → [微信授权登录]    → [首页/搜索/分类 发现商品]    → [商品详情页：查看图文、卖家信用、评价]    → [我想要 → IM 咨询/议价]  ──议价成功──┐    → [立即购买 → 确认订单]  ←────────────┘    → [微信支付（资金托管）]    → [卖家发货] → [物流在途]    → [确认收货 → 结算卖家]    → [双方互评] → [交易完成]
4.2 卖家主流程
[+ 发布] → [上传图片/视频] → [AI 识别预填] → [补充类目/成色/价格/运费]    → [提交 → 机审 + 人审] → [发布成功 → 进入首页推荐与搜索索引]    → [IM 接待买家咨询/议价]    → [订单待发货 → 填写物流单号]    → [已发货 → 跟踪物流]    → [买家确认收货 → 货款到账 → 可提现]
4.3 退款/售后流程
[买家发起售后] → 未发货：仅退款 ─→ 卖家 48h 未响应/同意 → 退款成功               └─ 已发货：退货退款 → 卖家同意 → 买家填退货物流 → 卖家签收验货                                               → 同意 → 退款成功                                               → 拒绝 → 平台介入（举证 + 判责）
4.4 关键流程规则表
规则点
 | 规则说明
 |
支付超时
 | 下单后 30 分钟未支付，订单自动关闭，库存释放
 |
发货超时
 | 支付后 72 小时未发货，系统提醒；第 5 天自动关闭并全额退款
 |
自动确认收货
 | 已发货后 10 天买家未操作，自动确认并结算
 |
结算延时
 | 确认收货后 T+1 结算至卖家可提现余额（风控可临时冻结）
 |
售后时效
 | 确认收货后 7 天内可发起售后；虚拟/定制类目不支持
 |
议价有效期
 | 议价卡片 24 小时内有效，过期失效需重新发起
 |
违规处置
 | 违禁品：直接下架 + 扣信用分；严重违规：冻结账户
 |

5. 系统架构（V1.0 单体 + V2.0 微服务演进）

7.5 单库索引策略（V1.0）
V1.0 采用 单 MySQL 8 主从、单库 ，不引入 ShardingSphere 分库分表（移至 V2.0）。单库在合理索引与读写分离下可支撑首版容量（见第 10 章）。
订单表 ：不按 buyer_id 分片；建立  (buyer_id, status)  与  (seller_id, status)  复合索引分别支撑买卖家视角查询；订单量增长后 V2 再按  buyer_id  取模分片。
商品表 ：单表 +  (user_id, status) 、 (category_id, status, refresh_at)  复合索引；同城与类目查询辅以 ES 召回后回查 DB 取详情。
消息表 ：单表；可选按  conv_id  哈希或按月  RANGE  分区（ 非分片 ，仍在单库）以控制单表体积；近 3 月热数据为主，历史归档走逻辑删除 + 冷表。
必备索引 ： item(user_id, status) 、 item(category_id, status, refresh_at) 、 order(buyer_id, status) 、 order(seller_id, status) 、 im_message(conv_id, id) 。
读写分离 ：写主读从，统计类查询（看板）走从库；热点商品详情走 Redis 多级缓存。

9.1 关键技术方案要点
发布一致性 ：商品写 MySQL 成功后发 RocketMQ（单节点），discovery 模块消费构建  ES 索引 （最终一致，容忍秒级延迟）；单体直连 ES，无独立 Search 服务。
库存/超卖 ：二手商品为单件（ stock=1 ），下单时用 Redis  SETNX item_lock:{id}  加锁 + 数据库乐观锁版本号双重保障（单体单实例下 DB 事务内即可，多实例仍走 Redis 锁）。
支付一致性 ：支付回调幂等（以  pay_no  唯一索引）； 本地消息表（outbox）+ RocketMQ 事务消息 保证"支付成功→订单状态变更"不丢，不依赖跨服务分布式事务。
延时关单 ：RocketMQ 延时消息（30min / 72h / 10d 等级）+  XXL-Job 每日补偿扫描 兜底（防止延时消息丢失）。
推荐冷启动 ：新用户用 LBS 同城热门 + 类目热度；新商品给予"新发布流量池"保底曝光（如 200 次）。规则版在 Redis/MySQL 实现，去模型服务。
IM 消息可靠 ：单体 Java WebSocket；客户端本地序号 + 服务端全局递增 seq，断线重连按 seq 增量拉取，保证不丢不重不序。
图片处理 ：客户端压缩至 ≤1080px 后上传，服务端异步转码多规格 + 水印 + 内容安全审核。
搜索排序 ： 相关性(BM25) × 时间衰减 × 距离衰减 × 卖家信用权重 × 商品质量分  综合打分（ES 实现）。
V2 拆分预留 ：模块边界清晰、跨模块仅经内部 service / 防腐层（ACL）访问；配置与第三方客户端集中在  common ，便于 V2 拆服务时独立部署与注册发现。

10.2 可用性与容量
服务可用性  ≥ 99.9% ：V1.0 通过  Nginx + 1~2 个单体实例  实现无单点（实例级故障由 Nginx 剔除）；核心链路（发布、详情、下单、支付）降级预案齐备。
V1.0 容量目标（单体） ：约  1 万 DAU、峰值 2000–3000 QPS、IM 长连接 5–10 万 （1~2 实例）。超过该量级再按 V2 微服务化扩容。
V2 容量目标（微服务化后） ：10 万 DAU、1 万 QPS 峰值、IM 长连接 50 万。
数据库主从切换 RTO ≤ 30s，RPO = 0（核心账务）。
每日全量备份 + binlog 增量，保留 30 天。

10.4 可维护性与扩展
模块化（按领域分包） ，进程内调用，共享 DB；配置中心（Nacos）为 V2 待办， V1.0 用 application + 环境变量 即可。
跨模块经内部 service / 防腐层（ACL）， 为 V2 服务拆分预留清晰边界 ，避免大规模重构。
全链路灰度（按 openid 灰度），支持一键回滚（Docker 镜像版本回退）。

14. 架构演进路线（V1.0 单体 → V2.0 微服务）
原则： 先跑通业务、后治理架构 。V1.0 单体快速上线验证需求与供给；当用户量与复杂度越过阈值，再按"增量拆分"引入微服务治理组件，避免早期过度设计。
能力
 | V1.0 状态
 | V2.0 动作
 | 触发条件（建议）
 |
服务拆分
 | 单体 Spring Boot（按领域分包）
 | 拆为 12 个领域服务（user/item/discovery/trade/pay/im/logistics/community/credit/risk/audit/admin）
 | 单体单库接近容量上限（见 10.2）或团队 > 8 人需独立部署
 |
API Gateway / BFF
 | Nginx（轻量）
 | 引入 APISIX / Spring Cloud Gateway + BFF 聚合层
 | 接口聚合/灰度/插件需求超出 Nginx 能力
 |
注册/配置中心
 | application + 环境变量
 | 引入 Nacos（服务发现 + 配置热更新）
 | 服务数 ≥ 5 且需动态配置
 |
分库分表
 | 单 MySQL 主从（单库）
 | 引入 ShardingSphere（订单按 buyer_id 分片、消息冷热分离）
 | 单表 > 5000 万行或主库写入瓶颈
 |
容器编排
 | Docker ×1~2 实例
 | 引入 K8s + HPA 弹性伸缩
 | 实例数 ≥ 4 或需自动扩缩容/多可用区
 |
IM 长连接
 | 单体 Java WebSocket
 | 拆独立 IM 服务（可选 Go/Netty），多可用区
 | IM 长连接 > 10 万 或 连接稳定性不达标
 |
链路追踪
 | Actuator + Prometheus + Grafana
 | 引入 SkyWalking + ELK
 | 跨服务调用排障需求出现
 |
数仓
 | 轻量埋点落库
 | 引入 Flink + ClickHouse/Hive 看板
 | 数据分析需求超出单库查询能力
 |
演进纪律 ：V2 拆分严格按模块边界与防腐层（ACL）进行，不破坏性改动业务语义；每次拆分独立上线、可灰度回滚；拆分优先级遵循"先瓶颈后平稳"（先拆 trade/pay/item 等高频写模块，再拆 discovery/community 等读模块）。
