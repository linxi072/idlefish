## 一、背景与问题

F-13.1 积分与 F-13.2 会员等级已落地，但从运营视角看仍是「静态的等级表 + 单向的积分流水」，不足以驱动留存与复购：

- **成长值维度单一**：当前以交易/积分为主，未覆盖「供给贡献」（发布优质商品、如实描述）与「社区贡献」（评价、验货配合、纠纷和解），导致高价值卖家与高频买家无法被区分激励。
- **权益未闭环**：等级权益多为展示性（标识、勋章），无实质兑换（如手续费折扣、曝光加权、专属客服），用户感知弱。
- **缺少衰减与回收机制**：长期不活跃用户等级永久保留，等级通胀、权益成本失控。
- **防刷不足**：积分发放缺少行为风控，存在自成交刷分、批量小号刷邀请的风险（F-13.4 邀请拉新已闭环，需配套防刷）。
- **用户侧不可见**：用户不知道「还差多少升级」，缺少进度与目标感，激励失效。

**现有可复用资产**：`PointCalculator` 已采用**纯函数范式**（离线可单测），成长值计算应沿用同一范式；F-10 券可作为权益兑换的落地载体（券发放/限领/唯一索引兜底已成熟）。

---

## 二、目标与非目标

**目标（可度量）**
- G1：等级体系上线后 **30 日复购率提升 ≥ 10%**、**卖家发布频次提升 ≥ 15%**。
- G2：成长值计算为纯函数，**Mockito 离线单测覆盖 100%**。
- G3：权益兑换**全链路闭环**（兑换 → 发券 → 使用 → 核销），兑换成功到可用 ≤ 10 秒。
- G4：刷分识别准确率 ≥ 85%，异常账户自动冻结积分发放。
- G5：用户端「升级进度」可见，等级权益说明页 UV 占比 ≥ 30% 活跃用户。

**非目标**
- 不做付费会员/订阅制（属独立商业模式，不在本项）。
- 不改变 F-13.1 既有积分发放口径（新增成长值维度，不重构存量）。
- 不做跨平台积分互通。
- 不做积分金融化（不可提现、不可转让、不可交易）。

| 角色 | 用户故事 |
|---|---|
| 买家 | 作为买家，我希望看到距下一等级还差多少，以便有动力继续交易 |

| 客服 | 作为客服，我希望在纠纷中查看用户成长与信用表现，以便辅助判断 |

## 四、需求清单（EARS）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| REQ-01 | Ubiquitous | 系统应**始终**将「积分」与「成长值」分离：积分可消耗，成长值不可消耗且决定等级 |
| REQ-02 | Event-driven | 当用户完成交易、发布、评价、验货配合、纠纷和解等行为时，系统应按规则累计成长值 |
| REQ-03 | Unwanted | 若行为被风控判定为刷分（自成交、关联账户、异常频次），系统应**不予**发放并冻结该账户发放通道 |
| REQ-04 | State-driven | 在成长值跨过等级阈值时，系统应即时升级并记录生效时间 |
| REQ-05 | State-driven | 在用户连续 N 日无有效活跃且成长值衰减后低于阈值时，系统应降级并提前通知 |
| REQ-06 | Ubiquitous | 成长值计算应实现为**纯函数**（入参确定 → 输出确定），可被离线单测覆盖 |
| REQ-07 | Event-driven | 当用户发起权益兑换时，系统应校验等级、库存、次数限制后原子扣减并发放（券/权益） |
| REQ-08 | Unwanted | 若权益库存不足或超出每日兑换上限，系统应**拒绝**兑换并明确提示原因 |
| REQ-09 | Ubiquitous | 积分与成长值流水应全量留痕（来源、规则版本、变更前/后、关联单号），可对账 |
| REQ-10 | Event-driven | 当用户被 F-17 工单判定为责任方时，系统应按规则扣减成长值 |
| REQ-11 | Ubiquitous | 用户端应展示当前等级、距下一等级进度与可享权益清单 |
| REQ-12 | Optional | 若运营配置了权益库存与有效期，系统应支持定时上下架与过期回收 |
| REQ-13 | Ubiquitous | 涉及金额的权益（手续费折扣/券面额）应以「分」为单位计算 |
| REQ-14 | Unwanted | 若规则配置发生变更，系统应**不得**追溯重算历史成长值（仅对新行为生效） |

## 五、流程说明

**成长值累计流程**
```
行为事件（交易完成/发布/评价/验货配合/纠纷和解/F-17 判责）
  → 行为校验（REQ-03 风控拦截）→ [命中刷分] 冻结 + 风控事件
  → 规则匹配（行为类型 × 用户角色 × 品类权重 × 规则版本）
  → 成长值计算（纯函数 REQ-06）
  → 写入流水（REQ-09）+ 更新累计值
  → 等级判定（REQ-04 升级 / REQ-05 衰减降级）
  → 通知用户（升级恭喜 / 降级预警）
```

**权益兑换流程**
```
用户发起兑换 → 校验（等级门槛 / 库存 / 每日次数 / 账户状态 REQ-03）
  → 原子扣减（成长值或积分）+ 发放权益（券走 F-10 发放链路，唯一索引兜底）
  → 失败回滚 → 成功通知（REQ-07、REQ-08）
```

**衰减流程**：定时任务扫描不活跃用户 → 按规则衰减 → 低于阈值降级 → 提前 7 日通知（REQ-05）。

**降级/回滚边界**：规则变更只影响新行为（REQ-14），历史成长值不追溯重算，避免账务与等级震荡。

## 六、交互说明

- **用户端会员页**：等级徽章 + 成长值进度条「距 Lv.N 还差 X 成长值」+ 权益清单（已享/待解锁）+ 成长值流水（近 30 日）。
- **兑换中心**：权益卡片（券/折扣/曝光加权/专属客服），展示库存、所需积分、限兑次数；兑换后「去使用」直达。
- **发布/交易后反馈**：轻量 toast「+X 成长值」，强化即时激励。
- **PC 后台（会员等级页扩展）**：
  - 成长值规则配置（行为类型、分值、权重、生效版本）
  - 等级阈值与权益映射（含库存、有效期）
  - 刷分名单与冻结/解冻操作
  - 成长值流水查询与对账报表（`analyticsMember` 扩展）
- **降级预警**：站内信 + 小程序订阅消息（需用户授权），说明降级时间与保留方式。

## 八、边界场景与异常状态

1. **退货/取消**：交易完成后发生退款 → 对应成长值应冲正（负向流水），避免刷分后立即退款。
2. **刷分对抗**：小额高频自成交、买卖双方互刷好评 → 关联账户识别 + 频次阈值 + 金额门槛（REQ-03）。
3. **等级通胀**：长期只升不降 → 衰减机制（REQ-05）+ 高等级占比监控。
4. **权益超发**：并发兑换导致库存击穿 → 原子扣减 + 唯一索引 + 库存校验双保险。
5. **规则变更**：新规则上线导致用户等级跳变 → 仅对新行为生效（REQ-14）+ 灰度期观察。
6. **纠纷判责**：F-17 判定卖家责任 → 扣减成长值（REQ-10），但需允许申诉成功后回补。
7. **账户封禁**：封禁期间成长值冻结，解封后是否回补需规则明确（默认不回补）。
8. **数据迁移**：存量用户无成长值 → 按历史交易/积分做一次性初始化，初始化值标记来源便于审计。

## 九、权限与合规

- 成长值/积分属用户虚拟财产，**不可单方面清零**；清零需提前公示并提供申诉通道。
- 衰减与降级规则须在用户协议与等级说明页明示，变更前提前通知（REQ-05）。
- 权益兑换涉及券/折扣，须明示使用条件、有效期、不可提现，避免误导。
- 刷分判定影响用户权益，须提供申诉与人工复核（误伤成本高于漏放）。
- 后台规则配置与库存变更需 RBAC 控制 + 操作留痕（谁/何时/原值/新值/规则版本）。
- 成长值相关的用户行为数据用于激励，不得超出约定目的使用。

## 十、验收标准（可勾选）

- [ ] 积分与成长值职责分离（REQ-01）。
- [ ] 交易/发布/评价/验货/和解等行为累计成长值（REQ-02）。
- [ ] 刷分行为不予发放并冻结通道（REQ-03）。
- [ ] 跨阈值即时升级并记录时间（REQ-04）。
- [ ] 不活跃衰减后降级且提前通知（REQ-05）。
- [ ] 成长值计算为纯函数，离线单测覆盖 100%（REQ-06）。
- [ ] 兑换原子扣减并发放权益（REQ-07）。
- [ ] 库存不足/超出上限拒绝兑换并提示原因（REQ-08）。
- [ ] 流水全量留痕可对账（REQ-09）。
- [ ] F-17 判责后按规则扣减（REQ-10）。
- [ ] 用户端可见等级/进度/权益清单（REQ-11）。
- [ ] 权益支持上下架与过期回收（REQ-12）。
- [ ] 金额类权益以「分」计算（REQ-13）。
- [ ] 规则变更不追溯重算历史成长值（REQ-14）。

## 十一、依赖与风险

| 类型 | 说明 | 应对 |
|---|---|---|
| 依赖 | F-13.1 `PointCalculator` 纯函数范式 | 成长值计算沿用同范式，便于离线单测 |
| 依赖 | F-10 券发放链路（限领 + 唯一索引） | 权益兑换复用券发放，避免重复造轮子 |
