# PRD｜ITER-U07 多端体验对齐（小程序 / PC 后台 / H5）

| 项 | 内容 |
|---|---|
| 编号 | ITER-U07 |
| 维度 / 优先级 | 用户体验 / **P2** |
| 状态 | 待评审 |
| 建议负责 | 前端负责人（多端）+ 设计负责人（规范）+ 产品负责人（路径定义） |
| 关联模块 | 微信小程序（原生）、pc-admin（Vite + Vue3 SFC，设计令牌 `:root` 已就绪）、H5（待建/规划）、F-09 小程序前端、ITER-U04 统一设计系统（令牌三层） |
| 被依赖 | ITER-U04（设计令牌与组件库是本项前提）、ITER-U02（信任标识跨端一致）、ITER-U03（PC 人效） |
| 编制日期 | 2026-10-02 |

---

## 一、背景与问题

三端（小程序 / PC 后台 / H5）长期**各自演进**，出现明显体验割裂：

- **视觉不一致**：小程序与 pc-admin 的颜色、圆角、间距、字号无统一来源（pc-admin 有 `:root` 令牌，小程序端基本是硬编码）。
- **术语不一致**：同一个业务对象在不同端叫法不同（如「维权工单 / 售后 / 纠纷」混用），用户与运营沟通成本高。
- **操作路径不一致**：同一任务（如发起维权）在小程序与 PC 的步骤、字段、校验规则不同，运营指导用户时无法给出统一话术。
- **状态表达不一致**：订单/工单状态在各端的名称与颜色不同（如「待发货」在一端是灰、另一端是橙），易误读。
- **H5 缺失**：分享链路（微信内打开商品/活动）缺少 H5 承接，用户未安装/未打开小程序时流失。
- **无障碍与适老未覆盖**：跨端一致性问题叠加 ITER-U05 要求，改造面更大。

**现有可复用资产**：pc-admin 已有设计令牌（`:root`，`--el-color-primary` 品牌暖橙覆盖）与响应式栅格；小程序为原生开发（需验证 CSS 变量基础库兼容性）；ITER-U04 正在把令牌抽为三层（基础/语义/组件）。

---

## 二、目标与非目标

**目标（可度量）**
- G1：建立**跨端设计令牌映射**：同一语义令牌在小程序 / PC / H5 三端取值一致，硬编码颜色**清零**。
- G2：**术语统一**：核心业务术语（对象名、状态名、操作名）三端一致，术语表覆盖 ≥ 50 条且被各端引用。
- G3：**核心路径对齐**：选定 5 条关键路径（发布商品、下单支付、查看订单、发起维权、查看售后进度），三端的步骤、字段、校验规则**完全一致**。
- G4：**状态表达统一**：订单/工单/商品状态的颜色与文案三端一致（状态枚举表单一来源）。
- G5：H5 **补齐分享承接**：商品详情、活动页、维权进度三类页面可在微信内 H5 打开并引导回流小程序。
- G6：**组件复用率 ≥ 60%**：三端共用同一套令牌与组件规范（PC 用 Vue 组件，小程序用自定义组件，规范一致）。

**非目标**
- 不做三端代码同构（不用 uni-app/Taro 重写小程序，成本与风险过高）。
- 不做 PC 后台与小程序的功能对等（两端用户与场景不同，仅对齐「用户可见的一致性要素」）。
- 不做 H5 全站（仅承接分享与回流场景）。
- 不改变后端接口契约（仅前端表达层对齐）。

## 三、目标用户与用户故事

| 角色 | 用户故事 |
|---|---|
| 买家/卖家 | 作为用户，我希望在不同端看到一致的说法与状态，以便不用重新学习 |
| 运营/客服 | 作为运营，我希望指导用户时话术与界面一致，以便降低沟通成本 |
| 前端 | 作为前端，我希望有统一令牌与术语表，以便减少各端反复确认 |
| 设计 | 作为设计，我希望设计规范被三端真实落地，以便保证品牌一致性 |

## 四、需求清单（EARS）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| REQ-01 | Ubiquitous | 系统应**始终**以跨端设计令牌（颜色/字号/间距/圆角/阴影）为样式唯一来源，禁止硬编码颜色值 |
| REQ-02 | Ubiquitous | 核心业务术语应以术语表为唯一来源，三端文案引用同一词条 |
| REQ-03 | Ubiquitous | 业务状态（订单/工单/商品/审核）应以状态枚举表为唯一来源，三端的名称与语义色一致 |
| REQ-04 | Event-driven | 当用户在任一端执行核心路径（发布/下单/查单/维权/售后进度）时，步骤、必填字段与校验规则应与其他端保持一致 |
| REQ-05 | Unwanted | 若某端因平台限制无法实现一致交互，应**记录差异并公示**，不得静默 divergent |
| REQ-06 | Ubiquitous | 金额在三端应统一以「分」为单位传输、以元为单位展示，格式（千分位/小数位）一致 |
| REQ-07 | Event-driven | 当用户在微信内打开分享链接时，系统应提供 H5 承接页并可引导回流小程序 |
| REQ-08 | Unwanted | 若 H5 承接页涉及交易/登录等敏感操作，应**跳转小程序完成**，不得在 H5 内处理 |
| REQ-09 | Ubiquitous | 空态、加载态、错误态在三端应使用统一的组件/文案模式（含无数据、网络异常、操作失败） |
| REQ-10 | Ubiquitous | 三端应统一支持无障碍基线（对比度 ≥4.5:1、可点击区域 ≥44px、支持系统字号） |
| REQ-11 | Event-driven | 当设计令牌或术语发生变更时，变更应同步至三端并留痕（版本号 + 变更说明） |
| REQ-12 | Unwanted | 若小程序基础库不支持 CSS 变量，系统应**提供编译期降级方案**（如生成静态样式），不得直接失效 |
| REQ-13 | Ubiquitous | 一致性应可被校验：提供三端一致性检查清单（颜色/术语/状态/路径）供评审与回归 |
| REQ-14 | Optional | 若需要视觉回归保障，应对关键页面建立截图基线对比（可先人工核对） |

## 五、流程说明

**令牌落地流程**
```
设计令牌（基础层 → 语义层 → 组件层，来自 ITER-U04）
  → PC：CSS 变量注入 `:root`（已具备）
  → 小程序：WXSS 变量 + [基础库不支持 REQ-12] 编译期生成静态样式
  → H5：同 PC 方案
  → 一致性校验（REQ-13）
```

**术语/状态治理流程**
```
建立术语表 + 状态枚举表（单一来源）
  → 三端引用（小程序 i18n/常量文件、PC 常量模块、H5 同 PC）
  → 变更需评审 → 同步三端 → 版本留痕（REQ-11）
```

**核心路径对齐流程**
```
选定 5 条关键路径 → 逐条拆解步骤/字段/校验/文案
  → 三端比对 → [存在差异] 判定：真缺陷修复 / 平台限制记录公示（REQ-05）
  → 对齐后写入一致性检查清单（REQ-13）
```

**H5 承接流程**：分享链接 → H5 落地页（只读展示）→ 需交互/交易 → 引导打开小程序（REQ-08）。

## 六、交互说明

- **令牌文档页**（内部）：展示三层令牌与三端取值映射，支持复制变量与查看使用位置。
- **术语表文档**（内部 + 客服可用）：词条、释义、禁用别名、使用端。
- **状态色规范**：语义色（成功/警告/危险/信息/进行中/已完成）在三端固定映射，状态标签组件各端实现一致（文案 + 色 + 图标）。
- **统一空/加载/错误态**：空态（插画 + 说明 + 主操作）、加载（骨架屏）、错误（原因 + 重试）三端同构。
- **H5 承接页**：商品详情（图/价/描述）、活动页、维权进度（只读）；底部常驻「打开小程序」引导按钮。
- **一致性检查清单**：按「颜色 / 术语 / 状态 / 核心路径 / 空错误态」五类逐项勾选，作为发布前卡口。

## 七、数据口径与指标

| 指标 | 口径 | 目标 |
|---|---|---|
| 硬编码颜色数 | 代码中非令牌的颜色值数量 | 0 |
| 术语一致率 | 三端文案一致的词条 / 术语表词条 | 100% |
| 状态表达一致率 | 三端名称与语义色一致的状态数 / 总状态 | 100% |
| 核心路径对齐率 | 已对齐路径 / 选定路径（5 条） | 100% |
| 组件复用率 | 复用规范组件的页面元素 / 总元素 | ≥ 60% |
| H5 回流率 | H5 引导打开小程序成功 / H5 访问 | ≥ 20% |
| 无障碍达标率 | 达标页面 / 关键页面 | 100%（对比度、点击区、字号） |
| 一致性回归缺陷 | 迭代中因不一致产生的缺陷数 | 逐迭代下降 |

**埋点**：`h5_landing_view`、`h5_to_mp_guide_click`、`h5_to_mp_success`、`consistency_defect`（缺陷来源分类）。

## 八、边界场景与异常状态

1. **小程序 CSS 变量兼容**：低版本基础库不支持 → 编译期生成静态样式（REQ-12），需验证目标基础库覆盖率。
2. **平台交互差异**：小程序无 hover、PC 无下拉刷新 → 允许交互形态差异但**结果一致**，差异需记录公示（REQ-05）。
3. **历史文案存量**：三端已有大量硬编码文案 → 分批替换（优先高频路径），避免一次性大改引发回归。
4. **状态色语义冲突**：同一状态在业务上需要强调（如「待处理」在运营侧要醒目）→ 语义色固定，强调通过位置/角标实现，不随意改色。
5. **H5 与小程序登录态割裂**：H5 无法直接获取小程序登录态 → 敏感操作必须跳小程序（REQ-08）。
6. **H5 分享被拦截/篡改**：分享链路被拦截 → 引导页需自解释（含商品关键信息），降低依赖。
7. **多端发布节奏不同步**：一端已更新另一端未发 → 版本兼容期需保证旧版可用（令牌与术语向后兼容）。
8. **无障碍与视觉设计冲突**：高对比要求与品牌淡色冲突 → 以达标为底线，调整令牌而非妥协。

## 九、权限与合规

- H5 承接页涉及商品与用户数据展示，须遵守最小必要原则（不展示卖家手机号/详细地址等）。
- 分享链接不得泄露用户隐私参数（如 userId 明文），使用一次性/不可反解的参数。
- 无障碍与适老要求（REQ-10）需满足监管基线，与 ITER-U05 协同。
- 引导回流小程序的文案不得误导（不虚假承诺优惠）。
- 术语与状态变更属对外表达变化，重大变更需评估用户告知义务。

## 十一、依赖与风险

| 类型 | 说明 | 应对 |
|---|---|---|
| 依赖 | ITER-U04 统一设计系统（令牌三层 + 组件库） | 本项是其跨端落地，必须在其之后 |
| 依赖 | pc-admin `:root` 令牌已就绪 | 作为 PC 侧基线，向小程序/H5 映射 |
| 依赖 | 小程序为原生开发 | 需验证 CSS 变量基础库兼容，必要时编译期降级 |
| 依赖 | ITER-U05 合规与无障碍 | 无障碍基线共用同一标准 |
| 风险 | 三端改造面大，易引发回归 | 分批替换（先高频路径），配截图回归 |
| 风险 | 小程序基础库兼容问题 | 目标基础库覆盖率调研 + 降级方案（REQ-12） |
| 风险 | H5 登录态割裂导致体验断层 | 明确只读边界，敏感操作跳小程序 |
| 风险 | 术语变更引发客服话术/文档批量更新 | 术语表版本化 + 变更公告 + 文档同步 |
| 风险 | 离线沙箱无法真机验证小程序 | 令牌与降级由构建产物静态检查，真机验证留本机 |
