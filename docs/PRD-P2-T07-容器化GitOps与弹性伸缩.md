## 一、背景与问题

F-15.4 已完成容器化（镜像与编排文件就绪），但**交付方式仍是手工/半自动**，缺少持续交付与弹性能力：

- **发布靠手工**：镜像构建与部署没有流水线化，环境间（dev/test/prod）配置漂移，回滚依赖人工记忆版本。
- **无法应对流量尖峰**：二手交易有明显波峰（大促、直播秒杀、早晚高峰），固定副本数要么浪费成本、要么峰值被打爆（ITER-F08 的瞬时脉冲尤其突出）。
- **配置与密钥管理分散**：配置混在镜像或启动参数里，密钥变更需重新构建镜像。
- **缺少渐进式发布**：无灰度/金丝雀，一次发布即全量，故障影响面大。
- **伸缩与应用指标未打通**：F-12.6 已有 Micrometer 指标，但未作为伸缩依据（传统 CPU 伸缩对 IO 密集型 Java 服务并不准确）。

**现有可复用资产**：F-15.4 容器化产物、Actuator 健康检查端点、Micrometer 指标、F-15.2 限流（伸缩前的保护闸）。

## 二、目标与非目标

**目标（可度量）**
- G1：发布**全流水线化**：合并到发布分支后自动构建 → 部署，**人工干预为零**（紧急审批除外）。
- G2：回滚**平均时间 ≤ 3 分钟**（一键回滚到上一可用版本）。
- G3：弹性伸缩生效：峰值 QPS 增长 3 倍时，**扩容在 2 分钟内完成**，错误率不升高。
- G4：配置与镜像**解耦**：配置变更无需重建镜像，密钥集中管理且可轮换。
- G5：支持**灰度/金丝雀发布**，可按流量比例放量并自动回滚（基于错误率/SLO）。
- G6：环境一致性：dev/test/prod 使用同一镜像，仅配置不同（消除「我这能跑」问题）。

**非目标**
- 不做多集群/多地域容灾（属更高级别可用性专项）。
- 不自建 K8s（采用云厂商托管集群，降低运维成本）。
- 不做服务网格（Service Mesh）引入（当前单体 + 少量服务，收益不抵复杂度）。
- 不改变应用代码的业务行为（仅补健康检查、优雅停机与无状态化改造）。

## 四、需求清单（EARS）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| REQ-01 | Ubiquitous | 系统应**始终**使用同一镜像贯穿 dev/test/prod，差异仅通过外部配置注入 |
| REQ-02 | Event-driven | 当发布分支有合入时，流水线应自动构建镜像、运行测试并部署到目标环境 |
| REQ-03 | Unwanted | 若单测/契约测试/构建任一失败，流水线应**阻断**部署，不得产出可部署镜像 |
| REQ-04 | Ubiquitous | 应用应暴露健康检查端点（存活/就绪），就绪失败时不接入流量 |
| REQ-05 | Event-driven | 当收到终止信号时，应用应优雅停机（停止接新请求、等待在途请求完成、释放资源） |
| REQ-06 | Unwanted | 若应用存在本地状态（本地缓存/本地文件/本地锁），应**改造为无状态**（外置到 Redis/OSS/分布式锁） |
| REQ-07 | State-driven | 在 CPU 或业务指标（QPS/队列积压）超过阈值时，系统应自动扩容副本 |
| REQ-08 | State-driven | 在负载回落并持续稳定期后，系统应自动缩容且缩容不中断在途请求 |
| REQ-09 | Ubiquitous | 副本数应设置上下限，且缩容速率应低于扩容速率（避免抖动） |
| REQ-10 | Event-driven | 当发布后错误率或时延超过 SLO 阈值时，系统应自动回滚到上一版本 |
| REQ-11 | Ubiquitous | 配置与密钥应外置（配置中心/Secret），**禁止**硬编码进镜像 |
| REQ-12 | Unwanted | 若密钥发生泄露或到期，应**支持**不重启/不重建镜像的热轮换 |
| REQ-13 | Ubiquitous | 每次部署应可追溯：镜像 tag、提交 SHA、部署人/触发源、时间、变更内容 |
| REQ-14 | Optional | 若采用 GitOps，集群状态应由仓库声明驱动，手工改集群应被检测并告警/自动纠正 |
| REQ-15 | Event-driven | 当发生扩容/缩容/回滚时，系统应发出通知并记录事件 |

## 五、流程说明

**持续交付流水线**
```
合入发布分支 → CI：编译（mvn -o 依赖需保障）→ 单测 → 契约测试 → 构建镜像（tag=提交SHA）
  → [任一失败 REQ-03] 阻断并通知
  → 推送镜像仓库 → 更新环境仓库的镜像声明（GitOps）
  → 集群同步（ArgoCD/Flux）→ 滚动/灰度发布 → 健康检查 → 完成
```

**灰度发布流程**
```
新版本小流量（如 5%）→ 观察错误率/时延/业务指标
  → [达标] 逐步放量（5% → 25% → 50% → 100%）
  → [超 SLO → REQ-10] 自动回滚 + 告警
```

**弹性伸缩流程**
```
指标采集（CPU + 业务指标：QPS、MQ 积压、接口耗时）
  → 超阈值持续 N 秒 → 扩容（上限内 REQ-07）
  → 负载回落且稳定 M 分钟 → 缩容（速率更慢 REQ-09）
  → 事件通知与记录（REQ-15）
```

**优雅停机流程**：收到 SIGTERM → 就绪探针置失败（摘流量）→ 等待在途请求/消息消费完成（超时上限）→ 关闭连接 → 退出（REQ-05）。

## 六、交互说明

- **流水线视图**：提交 → 构建 → 测试 → 镜像 → 部署各阶段状态可视，失败阶段可直达日志。
- **部署看板**：各环境当前版本（SHA）、部署时间、健康状态、副本数与伸缩历史。
- **灰度控制台**：流量比例滑块、实时指标对比（新/旧版本错误率与耗时）、一键全量/一键回滚。
- **告警通道**：部署失败、自动回滚、扩容达上限、副本不健康 → 企业微信/邮件通知（REQ-15）。
- **配置管理**：配置中心按环境/命名空间管理，变更需审批并留痕；密钥走 Secret 管理，支持轮换。
- **本地开发一致性**：提供 docker-compose 或 kind 本地环境，保证与集群行为一致（尤其 Redis/MySQL 依赖）。

## 七、数据口径与指标

| 指标 | 口径 | 目标 |
|---|---|---|
| 部署自动化率 | 自动部署 / 总部署 | 100%（紧急审批除外） |
| 回滚时长 | 触发回滚 → 旧版本恢复服务 | ≤ 3 分钟 |
| 扩容生效时长 | 指标超阈值 → 新副本就绪接流 | ≤ 2 分钟 |
| 发布失败率 | 失败的部署 / 总部署 | ≤ 5% |
| 自动回滚准确率 | 自动回滚中确为异常版本的占比 | ≥ 90% |
| 配置漂移事件 | 集群实际状态与仓库声明不一致的次数 | 0（GitOps 自动纠正） |
| 优雅停机丢请求数 | 停机期间失败请求数 | 0 |
| 资源利用率 | 峰值 CPU 平均使用率 | 40%~70%（避免过闲/过紧） |

**埋点/指标**：`deploy_total`、`deploy_failed`、`rollback_total`、`hpa_scale_up`、`hpa_scale_down`、`pod_not_ready`、`graceful_shutdown_duration`。

## 八、边界场景与异常状态

1. **有状态残留**：本地缓存/本地定时任务导致多副本行为不一致 → 必须外置（REQ-06），定时任务需选主或用分布式锁。
2. **伸缩抖动**：指标在阈值附近震荡导致频繁扩缩 → 冷却期 + 滞回区间（REQ-09）。
3. **扩容不及**：突发流量在扩容完成前已打爆 → 需配合限流（F-15.2）与预热副本/预留容量。
4. **数据库连接打满**：副本扩容导致连接池耗尽 → 连接池上限与副本上限联动评估。
5. **缩容中断请求**：缩容时副本被杀导致在途请求失败 → 优雅停机 + 就绪探针摘流（REQ-05）。
6. **消息消费与副本数**：消费者副本扩容受分区数限制 → 评估 Topic 分区数，避免消费能力无法水平扩展。
7. **镜像构建离线**：沙箱/内网环境无外网拉取基础镜像 → 需私有镜像仓库与基础镜像同步（与 ITER-T08 联动）。
8. **配置回滚遗漏**：回滚代码但配置未回滚 → 配置版本化并随发布一起回滚（REQ-13）。
9. **GitOps 手工改集群**：有人直接 kubectl apply 导致状态漂移 → 检测并自动纠正/告警（REQ-14）。

## 九、权限与合规

- 生产部署与回滚需 RBAC 控制，操作留痕（谁/何时/版本/原因）。
- 密钥集中管理，禁止入库与入镜像；访问密钥需授权并审计（REQ-11、REQ-12）。
- 部署日志与审计记录保留期需满足合规要求（默认 ≥ 180 天）。
- 灰度与回滚对外表现为短暂不可用，需评估是否触发 SLA 告知义务。
- 镜像需做漏洞扫描，高危漏洞阻断部署（纳入 REQ-03 门禁）。

## 十一、依赖与风险

| 类型 | 说明 | 应对 |
|---|---|---|
| 依赖 | F-15.4 容器化产物 | 在既有镜像/编排基础上补流水线与 HPA |
| 依赖 | F-12.6 Micrometer 指标 | 业务指标伸缩需先完成 ITER-T01 可观测性生产化 |
| 依赖 | ITER-T08 私有镜像/Maven 仓库 | 内网构建依赖私有仓库，两者需同期规划 |
| 依赖 | ITER-T02 资金压测 | 压测是验证伸缩效果的手段 |
| 风险 | 无状态化改造遗漏导致多副本异常 | 逐模块排查本地状态，压测多副本场景 |
| 风险 | 伸缩不及导致峰值仍在打爆 | 限流兜底 + 预热/预留 + 提前扩容策略（大促预设） |
| 风险 | 自动回滚误判（抖动触发） | 多指标联合判定 + 持续时间窗口 + 人工复核通道 |
| 风险 | 数据库/连接池成为扩容瓶颈 | 容量评估先行，必要时读写分离或连接池调优 |
| 风险 | 内网环境无法拉取公共镜像 | 私有仓库同步基础镜像（与 T08 联动） |
