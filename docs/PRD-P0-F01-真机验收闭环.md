## 一、背景与问题

**已具备**：F-11 生产基建去 Mock 已基本完成——`RealWechatEscrowServiceImpl`（微信支付 v3：JSAPI 下单 / 查单 / 退款 / 分账 / AES-256-GCM 解密 / RSA 验签）为唯一实现，支付回调**恒定验签**、分账**无条件执行**；F-11.5 验收用例与手册已就绪，配套脚本支持 `--mock`（离线）、`--live`（真机）、`--v3`（无效签名负向护栏）、`--v3-sign`（真实签名正向联调）。

**核心缺口**：上述能力**从未在真实商户号 + 真机环境执行闭环**，是当前唯一的功能缺口，直接阻断上线。

**用户痛点**
- 买家：支付后若回调丢失/延迟，订单长期停留在待支付，卖家不发货，交易卡死。
- 财务：重复入账或分账失败无告警 → 资损且难以追溯。
- 运营：IM 未真机压测，消息送达率与断线重连行为未知，售后沟通不可靠。

---

## 二、目标与非目标

**目标（可度量）**
- G1：支付全链路真机闭环成功率 100%（下单 → 支付 → 回调 → 订单 `paid` → 资金流水唯一 → 分账 → 提现）。
- G2：回调幂等 —— 重复/重放回调仅产生 1 条资金流水；金额不符回调被拒；伪造签名被拒。
- G3：IM 真机送达率 ≥ 99%，断线后指数退避重连成功，失效会话被清理。

**非目标**
- 不改动现有业务接口与表结构；不新增支付方式（仅限微信支付 v3）。
- 不做容量与性能压测（归属 ITER-T02）。
- 不重构资金网关逻辑（本项仅做真机验证与缺陷修复）。

## 三、目标用户与用户故事

| 角色 | 用户故事 |
|---|---|
| 买家 | 作为买家，我希望支付成功后订单立刻变为「已支付」，以便卖家及时发货 |
| 卖家 | 作为卖家，我希望收到明确的收款与分账结果，以便安排发货与提现 |
| 财务 | 作为财务，我希望每笔支付只产生一条资金流水且分账结果可查，以便日终对账 |
| 测试 | 作为测试，我希望用脚本一键复跑正向/负向用例，以便每次发版前回归 |

## 四、需求清单（EARS）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| REQ-01 | Ubiquitous | 系统应**始终**对支付回调执行 v3 验签，验签失败一律拒绝并记录，绝不静默放行 |
| REQ-02 | Event-driven | 当收到**金额与订单不符**的支付回调时，系统应拒绝入账并触发告警事件 |
| REQ-03 | Event-driven | 当同一回调**重复到达**时，系统应仅产生一条资金流水（条件更新 + affected 行网关） |
| REQ-04 | Unwanted | 若微信分账接口返回失败，系统应持久化失败原因并支持重试，**不得静默丢弃** |
| REQ-05 | Unwanted | 若提现申请提交且**未配置出款凭据**，系统应拒绝出款（硬网关），不得产生出款动作 |
| REQ-06 | State-driven | 在订单处于「已支付」状态期间，系统应触发发货通知与买卖双方双向通知 |
| REQ-07 | Event-driven | 当 IM 连接断开时，客户端应按指数退避重连直至成功，并清理失效会话 |
| REQ-08 | Optional | 若启用 `--v3-sign` 模式，脚本应使用商户私钥构造真实签名完成正向联调 |
| REQ-09 | Event-driven | 当真机验收发现缺陷时，应登记为缺陷事项并回链本 PRD，修复后重跑对应用例 |

## 五、流程说明

**主流程（支付回流）**
```
小程序 JSAPI 下单 → 微信支付 → 微信回调 /api/pay/**
  → [REQ-01] RSA 验签（失败即拒）
  → [REQ-02] 金额比对（不符即拒）
  → [REQ-03] 条件更新 + affected 行幂等网关（0 行即视为重复，直接返回成功）
  → 订单 status=paid，写资金流水（金额单位：分）
  → 分账执行 → 失败落库待重试
  → 双向通知（买家/卖家）+ 订阅消息触达
```

**异常分支**
| 分支 | 系统行为 | 兜底 |
|---|---|---|
| 验签失败 | 拒绝 + 记录 | 返回失败，微信侧重试 |
| 金额不符 | 拒绝入账 + 告警 | 人工介入核对 |
| 重复回调 | affected=0，直接成功 | 幂等，不重复入账 |
| 分账失败 | 落库 + 可重试 | 不阻断订单主流程 |
| 无出款凭据 | 拒绝出款 | 硬网关拦截 |

## 六、交互说明

- **小程序**：支付页 → 支付结果页（成功/失败明确态）；订单详情显示支付时间与流水号；IM 会话页显示连接状态与「重连中」提示。
- **PC 后台**：资金财务页可查资金流水与分账状态；提现审核页展示「凭据未配置」拦截提示；订单管理页可手动触发查单对账。
- **验收入口**：`scripts/pay-callback-sim.js --live` / `--v3-sign`（正向）、`--v3`（负向）；`scripts/im-loadtest.js --live`。

## 七、数据口径与指标

| 指标 | 口径 | 目标 |
|---|---|---|
| 支付闭环成功率 | 真机成功订单 / 发起订单 | 100% |
| 资金流水唯一率 | 每订单流水条数 = 1 的比例 | 100% |
| 回调幂等命中率 | 重复回调未产生新流水的比例 | 100% |
| IM 送达率 | 成功送达 / 发送总数 | ≥ 99% |
| 金额单位 | 全链路统一「分」 | 强制 |

---

## 八、边界场景与异常状态

1. 回调先于查单到达 / 回调晚于订单超时关单到达。
2. 分账接收方（卖家）账户异常或被冻结。
3. 真机与后端跨网络（NAT/防火墙）导致回调不可达 → 需公网可达回调地址。
4. 商户证书/私钥轮换后签名算法失效。
5. IM 弱网（地铁/电梯）下长时间断线重连。

---

## 九、权限与合规

- `/api/pay/**` 已鉴权放行（回调无需登录），其余接口需 Bearer JWT。
- 金额全链路「分」单位；出款凭据属敏感配置，仅运维可配，不得入库日志。
- 支付/退款日志脱敏（不包含完整商户密钥、用户身份证/银行卡全号）。

## 十、验收标准（可勾选）

- [ ] 真实商户号完成配置，`--v3-sign` 正向联调通过。
- [ ] `--v3` 无效签名被拒（负向护栏生效）。
- [ ] 金额不符回调被拒且不入账。
- [ ] 同一订单重复回调 3 次，资金流水仍为 1 条。
- [ ] 分账成功；人为制造分账失败时可查到失败记录并支持重试。
- [ ] 未配置出款凭据时提现被硬网关拦截，无出款动作。
- [ ] IM 真机送达率 ≥ 99%，断线重连成功。
- [ ] 全链路金额单位统一为「分」，与订单金额一致。
- [ ] 本轮发现缺陷全部登记并回链本 PRD。
