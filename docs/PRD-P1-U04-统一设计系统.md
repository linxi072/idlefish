| 状态 | **已实现**（V1.0.4 分支，本地提交待推送；高频页已迁移，其余页面按批次渐进替换） |

---

## 一、背景与问题

pc-admin 已建立 `global.css` 中的 `:root` 设计令牌（品牌色/中性色/`--el-color-primary` 暖橙覆盖/字体比例/间距/圆角/阴影），UI 一致性与响应式已改善。但**跨端与设计资产层面仍存在割裂**：

1. **令牌未被系统化**：令牌定义在 `global.css` 内，其他页面/组件部分仍硬编码颜色与尺寸（如部分组件内联样式），暗色模式（ITER-U03）若直接切换会出现漏网。
2. **三端视觉不一致**：pc-admin（Element Plus）、miniprogram（微信原生 WXSS）两套样式体系独立演进，颜色、圆角、间距、字号各自为政；信任标识（ITER-U02）等跨端元素难以保证一致。
3. **组件重复实现**：`PageHeader`、`TreeFlatTable` 等已抽为全局组件，但列表页的筛选栏、分页条、空态、状态标签等仍各页重复实现，改一处需改多页。
4. **无设计规范文档**：新页面/新同学加入时只能抄现有页面，风格漂移风险高。

---

## 二、目标与非目标

**目标（可度量）**
- G1：建立**统一设计令牌层**（颜色/字号/间距/圆角/阴影/层级），PC 端**硬编码颜色清零**（扫描校验）。
- G2：抽离**跨页复用组件**（筛选栏、分页条、空态、状态标签、页面头部、树形扁平表），重复实现下降 ≥ 60%。
- G3：产出**设计规范文档 + 令牌对照表**，小程序端按同一套色值与间距规范对齐（至少覆盖主色/成色/状态色/字号/间距）。
- G4：暗色模式（ITER-U03）基于令牌实现，切换后**无硬编码残留亮点**。

**非目标**
- 不做完整 Design Token 平台（JSON → 多端代码生成），先做人工维护的双端规范 + 脚本校验。
- 不重写现有页面为全新框架（渐进式替换）。
- 不强制小程序改用 Element Plus（保持微信原生，仅对齐色值与规范）。

## 四、需求清单（EARS）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| REQ-01 | Ubiquitous | 系统应**始终**通过设计令牌引用颜色/字号/间距/圆角/阴影，组件内不得硬编码这些值 |
| REQ-02 | Event-driven | 当执行样式扫描时，系统应能检出硬编码颜色并报告位置（作为 CI 或本地检查） |
| REQ-03 | Ubiquitous | 系统应**始终**提供跨页复用组件：页面头部、筛选栏、分页条、空态、状态标签、树形扁平表 |
| REQ-04 | Event-driven | 当新增页面时，应优先使用复用组件，重复实现需在评审中说明理由 |
| REQ-05 | Ubiquitous | 小程序端应**始终**使用与 PC 端一致的主色/状态色/成色语义（色值对照表） |
| REQ-06 | Event-driven | 当设计令牌变更时，PC 与小程序应同步更新，且变更需在规范文档中记录版本 |
| REQ-07 | Unwanted | 若组件在暗色模式下出现硬编码亮点，应视为缺陷并修复（令牌覆盖） |
| REQ-08 | Ubiquitous | 设计规范文档应**始终**包含：色板、字阶、间距、圆角、阴影、组件清单与用法 |
| REQ-09 | Event-driven | 当信任标识等跨端元素新增时，应在 PC 与小程序同时按规范实现（对齐 ITER-U02） |
| REQ-10 | Optional | 若引入图标库变更，应统一图标语义映射，避免同功能多图标 |

## 五、流程说明

**令牌与组件落地流程**
```
梳理现有样式 → 归纳令牌（global.css :root 已部分就绪，补全并分层）
  → 抽离复用组件（筛选栏/分页条/空态/状态标签等）
  → 页面渐进替换（优先高频页：订单/商品/用户/风控）
  → 扫描校验硬编码（REQ-02）→ 清零
  → 产出规范文档 + 双端色值对照表
  → 小程序端按对照表对齐（REQ-05）
```

**变更流程**：令牌变更 → 更新规范文档版本 → 双端同步 → 回归走查（REQ-06）。

## 六、交互说明

- **设计令牌分层**：`基础色`（品牌/中性/状态/成色）→ `语义令牌`（primary/success/warning/danger/text/background/border）→ `组件令牌`（按钮/卡片/表格）。语义层是暗色切换的关键（REQ-01/07）。
- **复用组件清单与用法**（REQ-03）：
  - `PageHeader`：标题 + 描述 + 面包屑 + 右侧操作插槽（已全局注册）。
  - `TreeFlatTable`：树形数据扁平表格（已全局注册，类目/机构/菜单在用）。
  - 新增：`FilterBar`（筛选栏，支持重置与模板）、`PageBar`（分页条）、`EmptyState`（空态）、`StatusTag`（状态标签）。
- **规范文档位置**：`docs/设计规范.md`（色板/字阶/间距/组件用法），与 `global.css` 令牌一一对应。
- **小程序对齐**：在小程序 WXSS 中定义同名 CSS 变量，色值与 PC 对照表一致。

## 七、数据口径与指标

| 指标 | 口径 | 目标 |
|---|---|---|
| 硬编码颜色数 | 扫描检出的硬编码色值数量 | **0**（PC 端） |
| 组件复用率 | 使用复用组件的页面 / 含该模式的页面 | ≥ 80% |
| 重复实现下降 | 重复代码块减少比例 | ≥ 60% |
| 双端色值一致率 | 小程序与 PC 同名令牌色值一致比例 | 100% |
| 暗色残留亮点 | 切暗色后仍为亮色的元素数 | 0 |
| 规范文档覆盖 | 规范中含定义的令牌比例 | 100% |

## 八、边界场景与异常状态

1. **第三方组件（Element Plus）内置色** → 需通过 `--el-*` 变量覆盖，无法覆盖的部分需记录在案并接受。
2. **ECharts 图表配色** → 图表色板需单独定义为令牌数组，暗色下切换主题。
3. **小程序原生限制** → 不支持部分 CSS 特性（如 CSS 变量在某些基础库版本），需确认最低基础库版本兼容。
4. **渐进替换期新旧并存** → 需标记「待替换」页面，避免半途而废。
5. **令牌过度抽象** → 语义层不宜过深，避免维护成本高于收益。

## 九、权限与合规

- 设计规范与组件库属团队资产，变更需评审（避免单人随意改令牌影响全局）。
- 小程序端需确认基础库版本对 CSS 变量的支持，避免低版本用户样式失效（兼容性风险）。
- 品牌色与标识使用需符合品牌规范，不得随页面自由发挥。

### 12.2 关键设计决策

1. **令牌文件与布局文件分离**：只有 `tokens.css` 允许原始色值，扫描器对其豁免；`global.css` 与所有 `.vue` 必须为 0。这样「0 硬编码」是可机器验证的硬约束，而非人工承诺。
2. **暗色只覆盖语义层**：不修改基础色，避免 `--text-inverse` 等由基础色派生的令牌被反转污染；Element Plus 组件色由官方 dark css-vars 提供，品牌主色在 `html.dark` 重新声明防止回退为默认蓝。
3. **图表配色运行时读取令牌**：ECharts 不解析 CSS 变量，`chartPalette()` 用 `getComputedStyle` 读取，并监听 `theme-change` 事件重绘，避免暗色下图表仍是亮色。
4. **组件向后兼容**：`PageBar` 同时派发 `change` 与旧 `current-change`/`size-change`；`StatusTag` 兼容 `{text,tag}` 旧字典格式。保证渐进替换不会一次性打断 27 个页面。
5. **首帧无闪烁**：`main.js` 在 `createApp` 前同步应用主题，且首次访问不把系统偏好固化为用户选择（仅主动切换时持久化）。
