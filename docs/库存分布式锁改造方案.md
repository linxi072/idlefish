## 1. 背景与目标

### 1.1 背景

本项目（idlefish-backend，二手交易小程序）已完成容器化建设（F-15.4）并具备多实例部署能力，Redis 已是系统唯一缓存实现（`RedisCacheAutoConfig` 恒定装配）。在上一轮技术债治理中，缓存批量失效（`keys()`→SCAN）、契约测试、券分页下沉等问题陆续闭环，但**库存并发一致性**仍旧停留在"单实例本地锁"阶段：

- `ItemService` 第 58 行的 `ConcurrentHashMap itemLocks` 注释明确写着——*"单实例应用级库存锁（防超卖）；**多实例需改用 Redis 分布式锁**"*。
- 代码自承认这是一个未完成的改造项，且随着容器化落地，多实例部署从"可能性"变为"默认形态"。

与此同时，核查还发现两个被掩盖的连带缺陷：**下单方法缺失事务**、**乐观锁在库存更新路径上未真正生效**。三者叠加，构成当前系统最高等级的资损与履约风险。

### 1.2 目标（可量化）

| 编号 | 目标 | 验收口径 |
|---|---|---|
| G1 | 多实例（≥2 实例）并发下单**零超卖** | 并发 100 线程 × 库存 10 → 成功建单 =10，库存终值 =0，无负值 |
| G2 | 消除 JVM 本地锁依赖，支持水平扩容 | 代码中不再出现 `itemLocks` 业务锁Map |
| G3 | 库存更新具备数据库层最终防线 | 即使 Redis 完全不可用，仍不超卖（降级到 DB 条件更新） |
| G4 | 消除 `itemLocks` 内存泄漏 | 堆内存中不再随 `itemId` 增长累积 `Object` 锁对象 |
| G5 | 锁等待时延可控 | P99 锁等待 ≤ 200ms；获取失败快速失败，不无限阻塞 |
| G6 | 修复下单事务缺失 | `createOrder` 多表写纳入单一事务，异常时全部回滚 |

### 1.3 非目标（本阶段不做）

- 不做秒杀/活动库存分段扣减、Redis 库存预热与异步落库（属于"秒杀专项"，见扩展方案）。
- 不引入 Redlock（多主 quorum），复杂度与当前单集群收益不匹配。
- 不改造商品数据结构、不加表字段（`Item.version` 已存在，直接复用）。

### 2.2 痛点归纳

- **P1｜多实例超卖**：实例 A 与实例 B 各自持有 JVM 内不同 `itemLocks`，互不感知。双方同时读到 `stock=1`，均判定充足并各自扣减，最终卖出 2 件、库存 -1。
- **P2｜库存泄漏（无事务兜底）**：`lockStock` 成功后，若 `payOrderMapper.insert` 失败或 `redeemCouponIfPresent` 抛异常，库存已扣却无对应订单，该商品永久少卖 1 件，且无任何补偿机制。
- **P3｜内存持续增长**：`itemLocks` 每个商品 ID 常驻一个 `Object`，商品数量增长即堆内存增长，长周期运行下不可回收。
- **P4｜热点竞争退化**：`synchronized` 在无竞争时很快，热点商品下所有线程串行，且因持有时间长（含 DB 往返与后续业务），吞吐急剧下降且无超时保护。

### 2.3 故障时序推演（双实例并发，库存 = 1）

```
时刻 t0  实例A: synchronized(lockA)  ← 实例B: synchronized(lockB)   （两把不同的本地锁，互不阻塞）
时刻 t1  实例A: SELECT stock → 1      实例B: SELECT stock → 1         （都读到 1）
时刻 t2  实例A: 判定 stock>=qty 通过  实例B: 判定 stock>=qty 通过
时刻 t3  实例A: UPDATE stock=0        实例B: UPDATE stock=0
时刻 t4  两笔订单均创建成功 → 实际卖出 2 件，库存 0，超卖 1 件
```

## 3. 整体技术方案

### 3.1 设计原则

1. **锁只用来降级争抢，正确性由 DB 保证**。Redis 锁降低并发冲突概率与 DB 压力；**是否真的能扣，最终由 `WHERE stock >= qty` 的条件更新说了算**。因此即便锁完全失效，也不会超卖——这是本方案的核心安全模型。
2. **语义分离**：不复用 `CacheService`。`CacheService` 接口契约明确写着 *"best-effort，缓存不可用不应影响主业务"*，而锁需要 **强语义（要么拿到，要么明确失败）**。两者混用会导致"缓存抖动被误判为锁失败"。
3. **锁粒度最小化**：按 `itemId` 加锁，绝不使用全局锁。
4. **fail-open 有界**：Redis 不可用时不阻断下单，降级到 DB 条件更新路径；但必须落告警指标，不允许静默。
5. **锁必须包住事务**：先加锁 → 再开事务 → 业务写 → 提交 → **finally 释放锁**。反过来（事务内加锁）会导致锁释放早于提交，其他实例读到未提交状态。

### 3.2 选型对比

| 候选方案 | 正确性 | 复杂度 | 性能 | 结论 |
|---|---|---|---|---|
| JVM 本地锁（现状） | 多实例 ✗ | 低 | 高 | **淘汰** |
| Redis `SET NX PX` + Lua 释放 | ✓（配合DB兜底） | 中 | 高 | **采纳（主）** |
| Redlock 多主 quorum | ✓ | 高 | 中 | 不采纳，当前单集群收益不匹配复杂度 |
| 仅 DB 条件更新 | ✓ | 低 | 中（热点抗压差） | **采纳（兜底 / 降级路径）** |
| `@Version` 乐观锁重试 | ✓ | 中 | 热点抖动 | 采纳为附加保护（本次修正生效） |

### 3.3 核心组件设计

**① `DistributedLock` 接口（新增，`common/lock/`）**

```java
public interface DistributedLock {
    /** 尝试获取锁；返回 token（释放时用于身份校验），失败返回 null。 */
    String tryLock(String key, long waitMs, long leaseMs);
    /** 释放锁（Lua 校验 token 一致才删除）。 */
    boolean unlock(String key, String token);
}
```

关键点：`tryLock` 返回 **token**（UUID），而非 boolean。释放时用 Lua 脚本校验 token —— **避免"A 的业务超时，锁自动过期，B 拿到锁，A 随后释放掉 B 的锁"这一经典误删问题**。

**② `RedisDistributedLockImpl`（新增）**

- 获取：`SET lock:{itemId} {token} NX PX {leaseMs}`，带短暂轮询等待（上限 `waitMs`）。
- 释放：Lua 脚本 `if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end`（**原子性必需**）。
- 令牌：`UUID.randomUUID().toString()`，保证跨实例唯一。

**③ `LockKeyBuilder`（新增）**：统一锁 key 命名 `idlefish:lock:item:{itemId}`，避免各业务散写字符串。

### 3.4 库存扣减的正确姿势（关键改动）

现状 `ItemService.lockStock` 使用 `updateById`（无条件），改为**条件更新**：

```sql
UPDATE item
   SET stock = stock - #{qty},
       version = version + 1
 WHERE id = #{id}
   AND stock >= #{qty}
   AND status = 'ONSALE'
```

- `affected rows == 0` → 说明库存不足或状态非法 → 抛 `BizException(Code.STOCK_NOT_ENOUGH)`（复用现有错误码）。
- `affected rows == 1` → 判定used zero 转 `LOCKED`（可在同一语句或紧随其后更新，需保证在同一事务）。
- 该语句本身即**幂等且原子的最终防线**：无论锁是否生效，都不可能扣成负数。

同时修正 `releaseStock` 为对称的条件更新（`stock = stock + qty`，并按结果判断是否恢复 `ONSALE`）。

### 3.5 正确的调用时序（必须遵守）

```
[Controller]
   │
[OrderService.createOrder]  ← 加 @Transactional（本次一并修复）
   │
   ├─ tryLock("idlefish:lock:item:{id}", wait=1s, lease=5s)   ← 事务前加锁
   │     └─ 失败 → 快速失败，抛 BIZ_BUSY（不无限等待）
   │
   ├─ BEGIN TRANSACTION
   │     ├─ lockStock（条件更新）
   │     ├─ orderMapper.insert
   │     ├─ payOrderMapper.insert
   │     └─ redeem 券/积分/活动
   ├─ COMMIT / ROLLBACK
   │
   └─ finally: unlock(key, token)                              ← 事务后释放
```

> ⚠️ **反模式警示**：若在 `@Transactional` 方法内部加 try-finally 释放锁，锁会在事务提交**之前**释放，其他实例读到中间态。**必须**在事务外层（或独立的编排方法）管理锁生命周期。本阶段采用"在 Service 内手动控制事务边界（或使用 `TransactionTemplate` 显式包住）"的方式实现，并在代码注释中固化该约束。

### 3.6 TTL 与续期策略

- `leaseMs` 初版 **5s**，`waitMs` **1s**。理由：下单链路 DB 往返正常在 100ms 内，5s 足以覆盖毛刺；即使超时，DB 条件更新仍能兜住正确性。
- **不引入看门狗（Watch Dog）自动续期**：复杂度与收益不匹配。业务超时时宁可快速失败并由用户重试，也不让线程长时间悬停。
- 配套：指标 `lock.acquire.timeout` 超阈值即告警，作为 TTL 调优依据。

### 3.7 降级链路

| 异常场景 | 行为 | 正确性保障 |
|---|---|---|
| Redis 连接失败 / 超时 | `tryLock` 捕获异常 → **降级为直接执行 DB 条件更新** | DB 条件更新保证不超卖 |
| Redis 主从切换短暂不可用 | 同上，并记录 `lock.degrade` 指标 + WARN 日志 | 同上 |
| DB 更新 affected=0 | 抛 `STOCK_NOT_ENOUGH` 业务异常 | 用户感知"已售罄" |
| 进程崩溃（锁未释放） | Redis TTL 到期自动释放 | 无死锁风险 |

### 3.8 观测指标（复用现有 `MetricsRegistry`）

| 指标名 | 含义 | 告警建议 |
|---|---|---|
| `lock.acquire.success` | 成功获取锁次数 | — |
| `lock.acquire.timeout` | 等待超时次数 | >0 持续告警（提示热点或 TTL 过短） |
| `lock.hold.time` | 持锁时长（ms） | P99 > 1s 告警 |
| `lock.degrade` | 降级到 DB 路径次数 | >0 立即告警（Redis 健康度） |
| `stock.update.fail` | 条件更新 affected=0 次数 | 突增提示库存争议 |

## 8. 回滚方案

### 8.1 回滚前提（重要）

本方案**不涉及任何数据库表结构变更**（复用已有的 `Item.version` 字段），因此**回滚不需要数据迁移或回滚脚本**，仅需代码回退。这是本方案刻意保持的低风险属性。

### 8.2 灰度开关（建议）

建议引入配置项 `idlefish.lock.enabled=true`（或 `lock.type=redis|off`），使"锁"这一层可独立关闭：

| 配置值 | 行为 | 用途 |
|---|---|---|
| `redis`（默认） | 走分布式锁 + DB 条件更新 | 正常态 |
| `off` | **跳过锁**，仅走 DB 条件更新 | 应急降级：Redis 异常且希望彻底绕开 |

> 注意：即使 `off`，DB 条件更新依然保证**不超卖**，只是并发争抢会有更多失败重试，因此 `off` 是**安全降级**而非"回到有缺陷的旧逻辑"。真正回到旧逻辑需 git revert。

### 8.3 回滚触发条件与步骤

| 触发条件 | 响应 | 执行人 |
|---|---|---|
| 下单成功率下降 > 5% | 切 `lock.type=off`，保住可用性 | R4 |
| Redis 持续不可用 | 切 `off`，排查 Redis | R4 |
| 出现库存为负（超卖） | 立即 `git revert` 到上一版本 + 数据修复 | R2+R5 |
| 锁等待 P99 > 1s 持续 10 分钟 | 调大 TTL / 排查热点商品 | R2 |

**回滚操作步骤**：① 修改配置（无需重启则走配置中心）→ ② 观察指标 → ③ 若仍异常，`git revert` 对应 commit → ④ 重新运行单测 → ⑤ 记录复盘。
