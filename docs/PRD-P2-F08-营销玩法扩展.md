## 一、背景与问题

F-10 券与 F-13.3 拼团秒杀已落地，覆盖了「打折」与「多人成团」两类基础玩法，但在大促与拉新场景下仍显单薄：

- **缺少爆发型玩法**：秒杀已有，但无直播带货场景的「直播间专属库存 + 口播发券」，大促峰值无法承接。
- **缺少裂变型玩法**：F-13.4 邀请拉新偏「关系链激励」，缺少「砍价」这类高传播、低成本的价格裂变。
- **缺少趣味性玩法**：抽奖可低成本拉动日活与停留，当前空白。
- **玩法烟囱风险**：每新增一个玩法就新增一套库存/限领/对账逻辑，历史经验（券、拼团）表明重复实现会带来一致性隐患。
- **大促稳定性未验证**：高并发下的库存击穿、超卖、重复发放，在 F-13.3 已有基础，但直播/抽奖的峰值模型不同（瞬时脉冲更强）。

**现有可复用资产**：`ActivityValidator` 纯函数校验范式、券的并发限领 + 唯一索引兜底、Redis 限流与 RocketMQ 削峰、营销 ROI 计算（F-14.5）均已成熟，新玩法应**复用同一套「活动内核」**而非各自实现。

---

## 二、目标与非目标

**目标（可度量）**
- G1：新增三类玩法（直播秒杀、砍价、抽奖）**共享同一活动内核**，内核复用率 ≥ 80%（库存/限领/时间窗/对账逻辑不重复实现）。
- G2：大促峰值下**零超卖、零重复发放**（库存与发放双校验 + 幂等）。
- G3：秒杀峰值 QPS 支撑 ≥ 现有拼团峰值的 3 倍（Redis 预扣 + MQ 异步落库）。
- G4：活动配置到上线**运营自助**（无需研发介入），配置生效 ≤ 5 分钟。
- G5：玩法核心校验为纯函数，**离线单测覆盖 100%**。

**非目标**
- 不做直播流媒体能力建设（仅对接直播间商品/库存/发券，视频流由第三方或后续专项）。
- 不做分销/多级返利（涉传销合规风险，明确排除）。
- 不做跨平台联合营销。
- 不改变 F-10 券与 F-13.3 拼团的既有逻辑（新玩法走内核，存量玩法逐步迁移）。

## 四、需求清单（EARS）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| REQ-01 | Ubiquitous | 系统应**始终**由统一「活动内核」提供库存扣减、限领校验、时间窗判定与对账流水，各玩法不得自行实现 |
| REQ-02 | Event-driven | 当活动开始时间到达时，系统应将库存预热至缓存并开放入口 |
| REQ-03 | Unwanted | 若库存不足或活动未开始/已结束，系统应**拒绝**参与并明确提示，不得出现超卖 |
| REQ-04 | Ubiquitous | 涉及金额的玩法（砍价底价、券面额、抽奖奖品价值）应以「分」为单位计算 |
| REQ-05 | Event-driven | 当用户发起抢购/砍价/抽奖请求时，系统应先经风控校验（设备/频率/账号画像），命中则拒绝 |
| REQ-06 | Unwanted | 若同一用户对同一活动重复提交（并发/重放），系统应通过幂等键保证**仅生效一次** |
| REQ-07 | State-driven | 在秒杀高并发期间，系统应采用「缓存预扣 + 异步落库」并保证最终一致，不阻塞下单主流程 |
| REQ-08 | Event-driven | 当砍价活动达成目标人数或底价时，系统应按规则结束并生成可下单资格 |
| REQ-09 | Ubiquitous | 抽奖概率与库存应可配置且**可审计**（概率配置留痕、中奖记录可追溯） |
| REQ-10 | Unwanted | 若抽奖奖品为实物或高价值，系统应**要求**补充收货信息与实名校验 |
| REQ-11 | Event-driven | 当活动结束或异常终止时，系统应回收未使用库存并结算补贴成本 |
| REQ-12 | Ubiquitous | 玩法校验逻辑应实现为纯函数（入参确定 → 输出确定），可被离线单测覆盖 |
| REQ-13 | Optional | 若运营配置了人群定向（新客/等级/地区），系统应在活动可见性与参与校验中同时生效 |
| REQ-14 | Unwanted | 若活动存在亏损风险（砍价底价低于成本），系统应**在配置阶段阻断**或要求审批 |
| REQ-15 | Event-driven | 当活动产生补贴时，系统应写入营销 ROI 数据源，供 F-14.5 BI 归因 |

## 五、流程说明

**统一活动内核（三类玩法共用）**
```
活动配置（时间窗 / 库存 / 限领 / 人群 / 风控等级）
  → 开抢预热（库存入缓存 REQ-02）
  → 参与请求 → 幂等校验（REQ-06）→ 风控校验（REQ-05）
  → 时间窗与库存校验（REQ-01 内核 + REQ-03）
  → 玩法特有规则（秒杀：抢购锁单 / 砍价：砍价金额计算 / 抽奖：概率抽取 REQ-09）
  → 结果落库（MQ 异步 REQ-07）+ 权益发放（券走 F-10）
  → 对账流水（REQ-01）+ ROI 归因（REQ-15）
```

**砍价流程**：发起 → 分享 → 好友助力（每人金额随机但总额受控，纯函数计算）→ 达底价或达人数（REQ-08）→ 生成下单资格（有效期内可用）。

**抽奖流程**：概率配置（可审计 REQ-09）→ 库存校验 → 抽取 → 实物/高价值奖品补充信息（REQ-10）→ 发放。

**降级流程**：缓存不可用 → 回落数据库强一致（性能下降但不超卖）；MQ 积压 → 限流 + 排队提示（不静默失败）。

## 六、交互说明

- **活动页（小程序）**：倒计时、库存进度条、参与按钮（置灰态明确原因：未开始/已抢完/已达上限）、规则说明浮层（必须明示概率、限领、有效期）。
- **直播间（小程序）**：主播端上架专属库存与口播券；观众端「点击抢」直达商品，库存实时刷新（WebSocket/轮询降级）。
- **砍价分享**：分享卡片含进度「已砍 ¥X，还差 N 人」，好友助力页一键助力（需登录）。
- **抽奖页**：奖品池展示（含概率）、抽奖动效、中奖记录与领取入口。
- **PC 后台（营销驾驶舱扩展）**：
  - 活动模板（秒杀/砍价/抽奖）向导式配置，含人群定向与风控等级
  - 库存与预算设置（亏损阻断 REQ-14，超阈值需审批）
  - 实时监控（参与 QPS、库存消耗、风控拦截量、异常账户）
  - 活动效果报表（GMV、补贴成本、ROI、拉新数）

## 七、数据口径与指标

| 指标 | 口径 | 目标 |
|---|---|---|
| 内核复用率 | 复用内核的玩法逻辑 / 玩法总逻辑 | ≥ 80% |
| 超卖/重复发放 | 实际发放 / 应发放 − 1 | 0 |
| 峰值 QPS | 秒杀峰值承载 | ≥ 拼团峰值 3 倍 |
| 风控拦截准确率 | 拦截中确为异常的占比 | ≥ 85% |
| 活动配置生效时长 | 配置保存 → 前端可见 | ≤ 5 分钟 |
| 纯函数单测覆盖 | 玩法校验分支覆盖率 | 100% |
| 活动 ROI | 活动带来 GMV / 补贴成本 | ≥ 3（视品类定基线） |
| 参与转化率 | 参与 → 下单 | ≥ 20% |

**埋点**：`activity_view`、`activity_join`、`activity_join_blocked`（含原因）、`bargain_assist`、`lottery_draw`、`live_stock_consume`、`activity_subsidy`。

## 八、边界场景与异常状态

1. **瞬时脉冲**：直播口播导致 QPS 数十倍跳变 → Redis 预扣 + MQ 削峰 + 限流排队（REQ-07），前端需排队反馈避免用户反复点击。
2. **库存回滚**：抢到未支付超时 → 库存回滚时机与并发回滚的正确性（需幂等 + 版本号）。
3. **砍价刷量**：同一好友多账号助力 → 设备/关系链识别（REQ-05）。
4. **概率争议**：抽奖概率不透明引发投诉 → 概率配置留痕 + 前端明示 + 中奖记录可查（REQ-09）。
5. **奖品超发**：并发抽取击穿库存 → 原子扣减 + 唯一索引兜底（REQ-06）。
6. **活动中途变更**：运营修改库存/价格 → 需明确已参与用户的权益不受损（快照机制）。
7. **跨天/跨时区**：活动时间窗以服务器时间为准，前端需校准。
8. **亏损风险**：砍价底价低于成本 → 配置阶段阻断（REQ-14）。
9. **MQ 积压**：异步落库延迟导致用户看到「成功」但库未落 → 以缓存结果为准展示，落库失败告警补偿。

## 九、权限与合规

- 抽奖属**有奖销售**，须明示奖品、概率、数量、时间、参与条件与领取方式；奖品价值不得超过法定上限（需法务确认）。
- 砍价不得构成虚假价格（虚构原价），须基于真实成交价或指导价口径。
- 活动规则变更不得损害已参与用户权益（活动快照 + 变更留痕）。
- 明确排除多级返利/分销（传销风险红线）。
- 风控拦截需提供申诉通道；实名/收货信息收集遵守最小必要原则。
- 后台活动配置与预算审批需 RBAC + 操作留痕。

## 十一、依赖与风险

| 类型 | 说明 | 应对 |
|---|---|---|
| 依赖 | F-13.3 `ActivityValidator` 纯函数与并发限领 | 抽象为活动内核，新玩法复用（避免烟囱） |
| 依赖 | Redis 限流 + RocketMQ 削峰（已真实接入） | 秒杀/抽奖强依赖，需先做容量评估 |
