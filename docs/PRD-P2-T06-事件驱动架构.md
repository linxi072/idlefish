## 一、背景与问题

RocketMQ 已**真实接入**（项目原则：外部组件一律真实实现，无 mock 开关），但当前使用方式是「点对点的异步解耦」，尚未沉淀为**领域事件**：

- **事件语义缺失**：消息体是随需定义的数据结构，无统一信封（事件 ID、类型、版本、发生时间、聚合根 ID、traceId），消费方需反查上下文。
- **跨域耦合仍是同步调用**：订单完成后要同步通知库存、积分、风控、BI、通知服务，任一依赖抖动会拖慢主流程甚至导致失败。
- **一致性靠人工约定**：本地事务与消息发送的原子性没有统一机制，存在「事务成功消息未发」或「消息发了事务回滚」的风险。
- **无法回放与追溯**：风控误判、BI 口径修正、新消费者接入历史数据时，缺少事件存储与重放能力。
- **可观测性断层**：MDC traceId 在异步消费侧断裂，排查跨服务链路困难。

**现有可复用资产**：RocketMQ 真实接入、ObservabilityFilter 已有 MDC traceId、资金链路已有「条件更新 + affected 行网关」的幂等范式——事件驱动应复用这些既有能力。

## 二、目标与非目标

**目标（可度量）**
- G1：沉淀核心领域事件（订单、库存、资金、商品、用户、工单）**≥ 15 类**，统一事件信封，版本化管理。
- G2：订单主流程同步外部依赖**减少 ≥ 60%**（改为事件驱动异步消费）。
- G3：消息**零丢失**：本地事务与发送通过事务消息/Outbox 保证，对账差异为 0。
- G4：消费端**幂等 100% 覆盖**，重复投递不产生业务副作用。
- G5：事件**可回放**：关键事件持久化 ≥ 90 天，支持按时间/聚合根重放。
- G6：异步链路 traceId **贯通率 100%**。

**非目标**
- 不做服务拆分（本项是单体内的事件驱动改造，服务化属 ITER-T04）。
- 不引入 Kafka/Pulsar 替换 RocketMQ（保持单一消息中间件）。
- 不做 CQRS / Event Sourcing 全量重构（仅事件通知，不改写入模型）。
- 不改变对外 API 契约（内部架构演进，对前端透明）。

## 四、需求清单（EARS）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| REQ-01 | Ubiquitous | 系统应**始终**使用统一事件信封：`eventId / eventType / version / occurredAt / aggregateId / traceId / payload` |
| REQ-02 | Ubiquitous | 事件 schema 应**版本化管理**，新增字段为可选、禁止破坏性变更（消费方需兼容旧版本） |
| REQ-03 | Event-driven | 当订单状态发生变更时，系统应发布对应领域事件（创建/支付/发货/完成/取消/退款） |
| REQ-04 | Event-driven | 当资金发生变动时，系统应发布资金事件（支付成功/分账/提现/退款），且金额以「分」为单位 |
| REQ-05 | Unwanted | 若本地事务未提交，系统应**不得**对外发布事件（通过事务消息或 Outbox 保证原子性） |
| REQ-06 | Unwanted | 若消息发送失败，系统应**不得**静默丢弃，须进入重试/补偿队列并告警 |
| REQ-07 | Ubiquitous | 消费端应**始终**实现幂等（事件 ID 去重表或业务状态机校验），重复投递不产生副作用 |
| REQ-08 | State-driven | 在消费失败且重试达上限时，消息应进入死信队列并可人工/自动重投 |
| REQ-09 | Ubiquitous | 事件应持久化存储 ≥ 90 天，支持按时间范围与聚合根 ID 查询与回放 |
| REQ-10 | Event-driven | 当事件发生并跨线程/跨服务传递时，traceId 应随事件传递并在消费侧注入 MDC |
| REQ-11 | Ubiquitous | 事件消费应可观测：积压量、消费耗时、失败率、重试次数纳入指标（复用 Micrometer） |
| REQ-12 | Unwanted | 若事件消费触发资金操作，系统应**必须**走既有幂等网关（条件更新 + affected 行校验） |
| REQ-13 | Optional | 若消费方需要历史事件（新接入或口径修正），系统应支持按条件回放且回放可限流 |
| REQ-14 | Ubiquitous | 事件发布与消费应有契约测试覆盖，schema 破坏性变更被 CI 阻断 |

## 五、流程说明

**事件发布流程（保证不丢）**
```
业务操作 → 本地事务内写入业务数据 + Outbox 事件记录（同一事务 REQ-05）
  → 事务提交后投递（事务消息或 Outbox 轮询发布）
  → [投递失败 REQ-06] 重试队列 → 仍失败 → 死信 + 告警
  → 投递成功标记 Outbox 为已发送
```

**事件消费流程（保证不重）**
```
消费 → traceId 注入 MDC（REQ-10）
  → 幂等校验（事件 ID 去重 / 状态机 REQ-07）
  → [已处理] 直接 ACK
  → 业务处理（资金类走幂等网关 REQ-12）
  → [失败] 重试（退避）→ 达上限 → 死信（REQ-08）
  → 成功 ACK + 指标上报（REQ-11）
```

**回放流程**：选择事件类型/时间范围/聚合根 → 限流重投 → 消费端幂等保证不产生副作用（REQ-13）。

**可观测流程**：Producer/Consumer 指标（TPS、耗时、积压、失败率）→ Micrometer → 看板 + 告警。

## 八、边界场景与异常状态

1. **事务与发送原子性**：先发消息后提交事务会导致「幽灵事件」→ 必须 Outbox 同事务写入（REQ-05）。
2. **消费乱序**：RocketMQ 不保证全局有序 → 消费端需基于状态机/版本号做乱序容忍（如「已完成」后收到「已支付」则丢弃）。
3. **重复投递**：网络抖动导致的重投 → 幂等去重表（eventId 唯一索引）。
4. **事件风暴**：一个操作触发大量事件引发级联 → 控制事件粒度，避免发散式级联发布。
5. **回放副作用**：回放触发短信/推送会骚扰用户 → 回放需标记 `replay=true`，副作用类消费者（通知/推送）默认跳过。
6. **schema 演进**：新增必填字段导致老消费方解析失败 → 只增可选字段，破坏性变更走新事件类型 + 双发过渡。
7. **MQ 不可用**：发布全部失败 → Outbox 堆积告警，主流程仍可用（异步降级），MQ 恢复后补偿投递。
8. **大消息**：payload 过大影响吞吐 → 事件只含关键字段与 ID，详情由消费方反查（避免事件臃肿）。

## 九、权限与合规

- 事件 payload 可能含个人信息（手机号、地址）→ 默认**脱敏或仅含 ID**，敏感字段需加密或访问控制。
- 事件查询/回放属高危操作 → RBAC 控制 + 操作留痕（谁/何时/条件/影响范围）。
- 事件留存 90 天需符合数据最小化与存储合规，超期自动清理（清理策略可配）。
- 死信消息含业务数据，丢弃操作需二次确认并留痕。
- 回放不得触发面向用户的通知（REQ 边界 5），避免合规投诉。
