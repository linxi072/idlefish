## 1. 背景与目标

### 1.1 背景

项目在**资金关键链路**上已有若干零散的正确性保障，但这些做法是"各自为战"而非体系能力：

- **支付回调**：已实现"验签 + 条件更新 + affected 行网关防重"（成熟且正确）。
- **结算认领**：`SettlementService.processDue` 采用 CAS 认领（`SettlementServiceTest` 已覆盖 3 场景）。
- **券领取**：依赖 `uk_user_coupon (user_id, coupon_id)` 唯一索引兜底限领。
- **提现出款**：配置硬网关（未配凭据绝不出款）。

然而在**用户主动发起的入口侧**（下单、退款申请、提现申请），缺乏统一的幂等能力。核查发现下单存在典型的 **check-then-act 竞态**（详见 §2.1），且因缺失事务，竞态穿透后会直接造成**重复扣库存 + 重复建单**的资损与履约事故。

本方案的目标，是把上述零散做法沉淀为**可复用、可声明、可观测统一幂等框架**。

### 1.2 目标（可量化）

| 编号 | 目标 | 验收口径 |
|---|---|---|
| G1 | 关键写接口具备声明式幂等 | 下单/退款申请/提现申请通过注解接入，零业务侵入 |
| G2 | 重复请求**不产生副作用** | 同一幂等 Key 重复调用 100 次 → 业务数据仅变更 1 次 |
| G3 | 幂等结果可回放 | 重复请求返回首次成功结果（同一 `orderNo`/`payNo`） |
| G4 | 消除下单 check-then-act 竞态 | 并发 50 次同 Key 下单 → 仅创建 1 笔订单、扣 1 次库存 |
| G5 | 幂等状态**不随业务回滚而丢失** | 业务异常回滚后，幂等记录保持在终态/可重试态 |
| G6 | 可观测 | 重复拦截次数、冲突次数、回放次数均有指标 |

### 1.3 非目标

- 不做消息队列消费端的幂等治理（RocketMQ 侧需另案）。
- 不改变既有支付回调的正确实现（本阶段仅"迁移接入"或保持原样，见 §5 M4）。
- 不实现跨服务的全局幂等协调（单服务内幂等即可）。

## 2. 现状问题与痛点分析

### 2.1 代码事实清单

| 问题 | 位置 | 证据 | 影响等级 |
|---|---|---|---|
| **下单幂等是 check-then-act 竞态** | `OrderService.java:103-108` | `findPendingOrder`（103，SELECT）→ `lockStock`（108，UPDATE）；两步之间无锁无原子约束 | 🔴 致命 |
| 无 DB 层唯一约束兜底 | `schema-mysql.sql` orders 表 | 仅有 `uk_order_no`(103)、`uk_order_pay_no`(104)，**无** `(buyer_id,item_id,status)` 联合唯一 | 🔴 致命 |
| 下单缺失事务 | `OrderService.java` | 全文 grep `@Transactional` **零命中** | 🔴 致命（放大竞态后果） |
| 幂等逻辑与业务耦合 | `OrderService.findPendingOrder:136-148` | 硬编码"同买家同商品待支付"规则，无法复用于退款/提现 | 🟡 高 |
| 幂等实现分散、无标准 | 支付回调/结算/券/提现各自实现 | 四种不同风格 | 🟡 中 |
| 重复拦截不可观测 | 无统一指标 | 无法回答"今天拦了多少次重复提交" | 🟢 低 |

### 2.2 痛点归纳

- **P1｜重复建单 + 重复扣库存**：用户连点两次"立即购买"，或前端超时重试，两个请求同时通过 `findPendingOrder` 的 null 检查 → 各自扣库存建单 → 同一买家同一商品出现两笔待支付订单。
- **P2｜退款/提现重复提交**：退款申请、提现申请目前无明显幂等保护，网络重试即可能重复发起，**直接关联资金安全**。
- **P3｜幂等语义不清晰**："处理中"的请求再次到达时该拒绝还是放行？现在没有统一定义，各接口行为不一致。
- **P4｜结果不可回放**：即便识别为重复，也无法返回"首次结果"，导致前端只能收到错误，体验差且易诱发用户再次操作。

### 2.3 与分布式锁方案的边界（重要）

| 维度 | 幂等框架（本方案） | 分布式锁（配套方案） |
|---|---|---|
| 解决什么 | **同一个请求被重复提交** | **不同请求并发争抢同一资源** |
| 作用点 | 入口（Controller/Service 边界） | 资源（如 itemId） |
| 失败语义 | 返回首次结果 / 提示处理中 | 快速失败 + 重试 |
| 共享约束 | **状态必须在事务外管理**（否则业务回滚会抹掉幂等记录） | **锁必须在事务外释放**（否则释放早于提交） |

> **二者互补而非替代**：下单场景应先过幂等层（拦重复），再由锁层保护库存。仅靠锁无法阻止"用户前后两次合法操作被误认为不同请求"，仅靠幂等无法阻止"两个真正不同的用户争抢最后一件"。

## 3. 整体技术方案

### 3.1 幂等 Key 规范

统一格式：`{bizType}:{bizKey}`

| bizType | bizKey 构成 | 示例 |
|---|---|---|
| `order.create` | `{buyerId}:{itemId}` | `order.create:2001:10088` |
| `refund.apply` | `{orderNo}:{type}` | `refund.apply:T20260929001:only_refund` |
| `withdraw.apply` | `{userId}:{amount}:{date}` | `withdraw.apply:2001:50000:20260929` |
| `pay.callback` | `{outTradeNo}`（迁移既有实现） | `pay.callback:P20260929001` |

**Key 解析**：`@Idempotent` 注解支持 SpEL 表达式，从方法参数中提取（如 `#dto.buyerId + ':' + #dto.itemId`），由 `IdempotentKeyResolver` 统一求值，避免各业务手写拼接。

### 3.2 三态模型（核心语义）

| 状态 | 含义 | 再次收到同 Key 时的行为 |
|---|---|---|
| `PROCESSING` | 首次执行中 | 未超时 → 抛 `BIZ_PROCESSING`（"处理中，请勿重复提交"）；**已超时 → 允许接管重试** |
| `SUCCESS` | 已完成 | **回放首次结果**（返回快照），不再执行业务 |
| `FAILED` | 失败且不可重试（或已重试耗尽） | **删除记录后重新执行**（保证用户可重试） |

> 超时基准：`PROCESSING` 记录携带 `expire_at`，默认 **30s**（远大于链路正常耗时），由清理任务兜底扫描。

### 3.3 存储选型（关键决策）

| 候选 | 强一致 | 性能 | 与项目契合度 | 结论 |
|---|---|---|---|---|
| Redis `SETNX` | △（主从异步） | 高 | 语义与 CacheService best-effort 冲突 | **辅助** |
| **DB 幂等表 + 唯一索引** | ✓ | 中 | 契合项目"唯一索引兜底"既有范式（`uk_user_coupon` 等） | **采纳（主）** |
| 分布式锁 + 内存态 | ✗ | 高 | 不可靠 | 淘汰 |

**结论**：采用 **DB 幂等表（强一致，终局保证）为主 + Redis 可选加速为辅**。这与项目已确立的资金安全范式一致——正如券领取依赖 `uk_user_coupon` 唯一索引兜底，幂等同样以数据库约束作为不可绕过的最后防线。

### 3.4 核心流程时序（AOP 拦截）

```
请求进入
   │
[IdempotentAspect]  ← Order 优先级高于事务拦截器
   │
   ├─ 1) 解析 Key（SpEL）
   │
   ├─ 2) INSERT idempotent_record(key, biz_type, status='PROCESSING', expire_at)
   │       【独立事务 REQUIRES_NEW，不随业务回滚而消失】
   │       ├─ 插入成功 → 继续 3)
   │       └─ 唯一键冲突 → 读既有记录，按三态分流：
   │             ├─ SUCCESS           → 返回 result 快照，【不执行业务】
   │             ├─ PROCESSING(未超时) → 抛 BIZ_PROCESSING
   │             ├─ PROCESSING(已超时) → 抢占接管（CAS 更新 owner+attempt），继续 3)
   │             └─ FAILED           → 删除后重新 INSERT，继续 3)
   │
   ├─ 3) 执行业务方法
   │       ├─ 成功 → UPDATE status='SUCCESS', result={快照}, cost=?
   │       └─ 业务异常 → UPDATE status='FAILED'；若标记 cleanupOnFail=true 则删除记录
   │
   └─ 4) 返回结果
```

**关键保障了 §2.2 的 P1**：并发两个请求只有一个能 INSERT 成功（唯一索引保证），另一个必然走"SUCCESS 回放"或"PROCESSING 拒绝"，不可能重复扣库存。

### 3.5 结果回放机制

- 记录 `result` 字段（JSON 快照，建议**仅存关键标识与金额**，避免存大对象）。
- 重复请求返回该快照，前端据此渲染同一种结果。
- **下单场景特别处理**：回放时建议返回已存在的 `pending` 订单信息（与现有 `findPendingOrder` 语义一致），从而平滑替换掉现网那段竞态逻辑。

### 3.6 与事务边界的协同（关键约束）

> ⚠️ **幂等记录的写入必须使用独立事务（`REQUIRES_NEW`），绝不能与业务同处一个事务。**

原因：若与业务同事务，业务失败回滚会把幂等记录一并回滚 → 记录消失 → 用户重试时再次执行 → 幂等完全失效。

实现路径（二选一，建议前者）：
1. **AOP 优先级高于事务拦截器**（`@Order` 值更小），在事务开启前写入，且用 `TransactionTemplate(REQUIRES_NEW)` 封装幂等写操作。
2. 使用 `Propagation.REQUIRES_NEW` 的独立 Service 方法写幂等表。

这与配套方案中"锁必须在事务外释放"是**同一类约束**，应在团队规约中统一固化。

### 3.7 与既有实现的迁移策略

| 既有实现 | 处理方式 | 说明 |
|---|---|---|
| 支付回调（验签+条件更新+affected） | **保持原样**，仅登记接入清单 | 已正确且经过 F-11.5 验证，不引入变更风险 |
| 结算 CAS 认领 | **保持原样** | `SettlementServiceTest` 已覆盖 |
| 券 `uk_user_coupon` 唯一索引 | **保留索引**（继续作为最后防线），上层可选接入注解以获得"回放"能力 | 索引是兜底，不删除 |
| 下单 `findPendingOrder` | **由幂等层替代**（人工比对后移除旧竞态逻辑） | 消除双逻辑 |

### 3.8 观测指标（复用 `MetricsRegistry`）

| 指标名 | 含义 | 告警建议 |
|---|---|---|
| `idempotent.hit` | 命中重复（SUCCESS 回放）次数 | 突增提示前端重试风暴 |
| `idempotent.conflict` | 唯一键冲突次数 | — |
| `idempotent.processing` | 命中"处理中"次数 | 持续 >0 提示 TTL 过短或慢接口 |
| `idempotent.replay` | 结果回放次数 | — |
| `idempotent.record.count` | 表行数 | 超阈值提示清理任务异常 |

### 3.9 数据清理策略

- 新增记录带 `expire_at` 索引。
- 复用项目既有的调度能力（`TradeApplication` 已 `@EnableScheduling`，已有 `TradeScheduler`/`SearchScheduler` 等先例）新增 `IdempotentCleanupJob`，每日清理过期记录。
- 保留期建议：**SUCCESS 记录保留 7 天**（足够覆盖回滚/对账排查），`FAILED` 保留 1 天。

## 8. 回滚方案

### 8.1 回滚复杂度说明

本方案**涉及数据库新增表**，因此回滚需要区分两种情况：

| 情况 | 处理 |
|---|---|
| 仅回滚业务接入（推荐优先） | 移除 `@Idempotent` 注解即可，**框架与表可保留**（表为空 key 不影响任何现有逻辑） |
| 完整回滚（含表） | `DROP TABLE idempotent_record`（此时表已无业务依赖），**无需数据迁移** |

> 幂等表是**纯新增附属表**，不修改任何既有表结构，因此**不存在数据损坏风险**——这是关键的低风险属性。

### 8.2 灰度开关

建议配置 `idlefish.idempotent.enabled=true`：

| 配置值 | 行为 | 用途 |
|---|---|---|
| `true`（默认） | 走完整幂等逻辑 | 正常态 |
| `false` | AOP 直接放行，不写幂等表 | **兜底逃生**：Key 设计缺陷导致误杀时的快速止血 |

> 注意：`false` 会退回"无幂等"状态（即现状），因此仅作临时止血，需在 24h 内定位根因。

### 8.3 回滚触发条件与步骤

| 触发条件 | 响应 | 执行人 |
|---|---|---|
| 正常下单被误判重复（Key 误杀） | 切 `enabled=false` 止血 → 修 Key 规则 | R4→R2 |
| 幂等表慢查询影响主链路 | 切 `enabled=false` → 优化索引/添加 Redis 前置 | R4→R5+R2 |
| 提现/退款因幂等卡单 | 立即 `enabled=false` → 人工核对是否有重复出款 | R2+R3 |
| 清理任务异常导致表膨胀 | 暂停任务 → 手动分批清理 | R4 |

**回滚操作步骤**：① 切配置 `enabled=false` → ② 观察订单/资金指标恢复 → ③ 若需完整回滚，`git revert` 业务接入 commit → ④ 数据侧确认无重复扣款/重复出款 → ⑤ 记录复盘。
