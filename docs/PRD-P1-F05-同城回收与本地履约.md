# PRD｜ITER-F05 同城回收与本地履约

| 项 | 内容 |
|---|---|
| 编号 | ITER-F05 |
| 维度 / 优先级 | 功能完善 / **P1** |
| 状态 | 待评审 |
| 建议负责 | 产品负责人（业务规则）+ 后端负责人（履约/机构） |
| 关联模块 | `Organization` 机构管理（已扁平为表格）、RBAC 角色管理、`logisticsTrack` 物流轨迹、F-14.2 推荐（同城因子）、F-17 售后工单 |

---

## 一、背景与问题

二手交易的**大件与低值品类**存在结构性难题：

- **大家电/家具**（客单价低、体积大、运费高）：快递成本可能超过商品本身价值，买卖双方都不愿承担 → 交易无法成立。
- **3C 数码闲置**：用户有强烈的「以旧换新/变现」需求，但嫌发布与议价麻烦 → 供给流失。
- **当前系统仅有标准快递链路**（`logisticsTrack`），**无同城自提、无上门回收、无区域化运营**。

**行业趋势**：本地生活与上门回收（3C/家电/衣物）已成为二手平台获取供给与降低履约成本的主流方式；循环经济政策亦鼓励规范回收。

**现有可复用资产**：`Organization` 机构（已支持层级，可映射区域运营中心/回收站点）、推荐已含同城因子、物流轨迹可复用。

---

## 二、目标与非目标

**目标（可度量）**
- G1：大家电/家具类目**成交转化率提升 ≥ 20%**（同城自提/配送降低运费门槛）。
- G2：上门回收**供给量**达到目标：上线 3 个月内回收单占新增供给 ≥ 10%。
- G3：同城订单**平均履约时长**较跨城快递下降 ≥ 30%。
- G4：区域机构可独立运营本区域回收与履约数据（为 ITER-T05 打样）。

**非目标**
- 不自建回收物流车队（接入第三方回收/同城配送服务商）。
- 不改变现有跨城快递链路与订单主流程（同城为**新增可选履约方式**）。
- 不做回收后的翻新再销售（仅回收入库/环保处置，商业模式另议）。

## 三、目标用户与用户故事

| 角色 | 用户故事 |
|---|---|
| 卖家（大件） | 作为卖家，我希望选择同城自提或同城配送，以便避免高额运费、促成交易 |
| 卖家（闲置变现） | 作为卖家，我希望一键申请上门回收，以便不用发布与议价就能变现 |
| 买家 | 作为买家，我希望筛选同城商品并自提，以便当面验货、降低风险 |
| 区域运营 | 作为区域运营，我希望只看到本区域的回收单与履约数据，以便独立运营 |
| 平台 | 作为平台，我希望回收带来低成本供给，以便补充长尾品类 |

## 四、需求清单（EARS）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| REQ-01 | Event-driven | 当卖家发布商品并选择「同城自提」时，系统应在商品页与列表页标注同城标识并支持按同城筛选 |
| REQ-02 | Event-driven | 当用户提交上门回收申请时，系统应基于品类与地址给出预估回收价并生成回收单 |
| REQ-03 | State-driven | 在回收单处于「待上门」状态期间，系统应允许用户取消，且取消后不产生任何费用 |
| REQ-04 | Event-driven | 当回收员上门完成质检后，系统应按最终质检等级调整回收价并经用户确认后放款 |
| REQ-05 | Unwanted | 若用户拒绝调整后的回收价，系统应取消回收单并安排退回，**不得**强制成交或扣费 |
| REQ-06 | Event-driven | 当同城配送单产生时，系统应接入第三方同城配送并回传轨迹至 `logisticsTrack` |
| REQ-07 | Ubiquitous | 系统应**始终**将回收金额与配送费用以「分」为单位记账，并纳入资金流水与对账（ITER-T02） |
| REQ-08 | Event-driven | 当回收单归属某区域机构时，系统应仅向该机构角色展示本区域数据 |
| REQ-09 | Unwanted | 若第三方回收/配送服务不可用，系统应将回收单置为「服务暂不可用」并通知用户，不得静默失败 |
| REQ-10 | Event-driven | 当用户选择同城自提并完成交易时，系统应引导双方当面验货确认，并缩短确认收货时效 |
| REQ-11 | Optional | 若品类属于回收白名单（3C/家电/衣物），系统应在发布页展示「一键回收」入口 |

## 五、流程说明

**上门回收主流程**
```
用户选择品类 + 填地址/成色 → 系统给预估回收价（REQ-02）
  → 提交回收单（待上门）
  → 回收员上门质检 → 最终定价
     ├─ 用户接受：确认 → 放款（分）→ 入库/环保处置
     └─ 用户拒绝：取消 → 退回，无费用（REQ-05）
```

**同城自提/配送主流程**
```
卖家发布选「同城自提」→ 商品打同城标识（REQ-01）
  → 买家筛选同城 → 下单 → [可选]同城配送（REQ-06，轨迹回传）
  → 当面验货 → 确认收货 → 放款（REQ-10）
```

**异常分支**：服务商不可用（REQ-09）、用户取消（REQ-03）、质检争议（转 F-17 工单）。

## 六、交互说明

- **发布页**：大件品类增加「履约方式」选择（快递/同城自提）；回收白名单品类展示「一键回收」入口（REQ-11）。
- **回收页**：品类选择 → 成色/配置勾选 → 预估价展示（明确「最终以质检为准」）→ 地址与时间预约 → 提交。
- **商品列表/详情**：同城标识 + 「仅看同城」筛选开关。
- **订单详情**：同城配送轨迹（复用物流时间轴）；自提单展示自提地址与验货提示。
- **PC 后台（新增回收管理）**：回收单列表（状态/区域/品类）、质检结果、放款记录、区域数据隔离（REQ-08）。

## 七、数据口径与指标

| 指标 | 口径 | 目标 |
|---|---|---|
| 大件品类转化率 | 同城大件成交 / 大件浏览 | 提升 ≥ 20% |
| 回收供给占比 | 回收单 / 新增供给 | ≥ 10%（3 个月内） |
| 同城履约时长 | 下单 → 完成中位时长 | 较跨城下降 ≥ 30% |
| 回收单完成率 | 完成放款 / 提交总数 | ≥ 70% |
| 报价争议率 | 拒绝最终价 / 上门质检总数 | < 20% |
| 金额口径 | 回收款、配送费统一「分」 | 强制 |

**埋点**：`recycle_apply`、`recycle_quote_return`、`recycle_confirm/reject`、`local_filter_use`、`local_order_create`、`logistics_local_track`。

## 八、边界场景与异常状态

1. 用户虚报成色，上门质检后价格大幅下降 → 需明确「最终以质检为准」并允许无费用取消（REQ-05）。
2. 上门地址不可达/用户爽约 → 需爽约规则与黑名单。
3. 回收品涉及违禁/赃物风险 → 需身份核验与来源声明，命中风控转人工。
4. 同城自提纠纷（当面验货后反悔）→ 需明确自提交易的责任转移节点。
5. 第三方服务商区域性不可用 → 按区域灰度开关，不可用区域隐藏入口。
6. 大件配送损坏 → 需保价与赔付规则。

---

## 九、权限与合规

- 回收涉及**二手商品来源合法性**，需用户签署来源合法声明；3C 需核对序列号，赃物风险品类需身份核验。
- 上门回收涉及**入户服务安全**，需服务商资质审核与行程可追溯。
- 用户地址属敏感个人信息，需加密存储、脱敏展示，且仅履约必要方可见。
- 区域机构数据隔离需 RBAC 控制（REQ-08），越权访问测试必须通过（ITER-T05）。
- 回收定价与放款须纳入资金对账（ITER-T02），避免账外资金。

---

## 十、验收标准（可勾选）

- [ ] 同城自提商品有标识且支持「仅看同城」筛选（REQ-01）。
- [ ] 上门回收可提交并给出预估价（REQ-02）。
- [ ] 「待上门」状态可无费用取消（REQ-03）。
- [ ] 质检后调价需用户确认，拒绝则取消退回且无费用（REQ-04/05）。
- [ ] 同城配送轨迹回传至 `logisticsTrack`（REQ-06）。
- [ ] 回收款与配送费以「分」入账并进入对账（REQ-07）。
- [ ] 区域机构仅可见本区域数据（REQ-08）。
- [ ] 服务商不可用时明确提示而非静默失败（REQ-09）。
- [ ] 自提单引导当面验货（REQ-10）。
- [ ] 白名单品类发布页展示「一键回收」（REQ-11）。
