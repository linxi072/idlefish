## 一、背景与问题

项目已有契约一致性测试 `ContractConsistencyTest`，用于校验后端接口契约 JSON 与前端（`pc-admin/src/api`）调用是否一致，当前覆盖 **136 个端点**。

**现存问题**
1. **契约清单硬编码**：测试类内写死 8 个契约文件名，**不自动扫描目录** —— 新增契约文件若忘记手动登记，该契约**完全不被校验**，形成静默盲区。
2. **无 CI 门禁**：契约不一致是否阻断合流未明确；前后端接口变更可能直到联调甚至上线才暴露。
3. **单向校验**：当前主要是「后端契约 vs 前端调用」的比对，缺少**消费者驱动契约**（前端声明期望 → 后端满足），新增字段/删除字段的兼容性判定不明确。
4. **维护成本随端点数增长**：136 → 未来 200+ 端点，硬编码清单与人工登记不可持续。

**为什么建议提前到第一批**：后续 ITER-F03~F08、U01~U04 均涉及大量接口变更，早建卡口可显著降低回归成本；越晚建立，历史债越大。

---

## 二、目标与非目标

**目标（可度量）**
- G1：契约清单**自动扫描**，新增契约文件无需手动登记即纳入校验，覆盖率 100%。
- G2：契约不一致在 **CI 阶段阻断合流**（门禁生效），不一致项零漏网。
- G3：明确**兼容性判定规则**：新增可选字段/新增端点视为兼容；删除字段、改类型、改语义视为不兼容并阻断。
- G4：契约测试**离线可跑**（不依赖 MySQL/网络），纳入 `mvn -o` 可执行的测试集。

**非目标**
- 不引入重型契约平台（如 Pact Broker 私有化部署）作为前置条件；先用轻量自研 + CI 脚本。
- 不改变现有接口业务语义（本项只做校验机制）。
- 不做性能契约（响应时延阈值）校验，属 ITER-T01 可观测性范畴。

## 四、需求清单（EARS）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| REQ-01 | Ubiquitous | 系统应**始终自动扫描**契约目录下的全部契约文件纳入一致性校验，不得依赖手写清单 |
| REQ-02 | Event-driven | 当新增契约文件但未被扫描覆盖时，测试应能发现该文件（覆盖率自校验），否则视为缺陷 |
| REQ-03 | Unwanted | 若后端契约与前端调用不一致（路径/方法/字段名/必需性），测试应失败并输出**精确到端点与字段**的 diff |
| REQ-04 | Unwanted | 若变更删除了既有字段、或改变了字段类型/枚举语义，系统应判定为**不兼容**并阻断合流 |
| REQ-05 | Event-driven | 当变更仅新增可选字段或新增端点时，系统应判定为**兼容**并放行，但需在报告中列出 |
| REQ-06 | Ubiquitous | 契约测试应**始终**可在离线环境运行（纯文件解析 + Mockito，不依赖 MySQL/网络） |
| REQ-07 | Event-driven | 当 CI 执行时，契约测试应作为**阻断门禁**在合流前运行，失败则不允许合流 |
| REQ-08 | Unwanted | 若契约文件本身格式非法（JSON 解析失败/缺字段），测试应明确报错定位到文件与行 |
| REQ-09 | Event-driven | 当契约变更被判定为不兼容时，系统应输出迁移指引（影响的前端调用位置清单） |
| REQ-10 | Optional | 若需临时豁免某契约不一致，应支持显式豁免配置（带原因与过期时间），且豁免项在报告可见 |

## 五、流程说明

**契约校验流程（改造后）**
```
扫描契约目录（自动，REQ-01）
  → 解析契约 JSON（格式非法则报错定位，REQ-08）
  → 与前端 api 模块调用比对（路径/方法/字段/必需性）
  → 兼容性判定（REQ-04/05）
     ├─ 兼容（新增可选字段/新端点）→ 记录 → 放行
     └─ 不兼容（删字段/改类型）→ 输出 diff + 影响清单（REQ-03/09）→ 阻断
```

**CI 门禁流程**
```
PR 提交 → CI 触发 → 编译 → 单测 → 契约测试（REQ-07）
  → 失败：阻断合流，PR 展示 diff 与影响清单
  → 通过：允许合流
```

**豁免流程**：确有合理原因 → 在豁免配置登记（原因 + 过期时间 + 责任人）→ 报告可见 → 到期提醒清理（REQ-10）。

## 六、交互说明

- **CI 报告**：PR 检查项展示「契约一致性」结果；失败时以注释形式贴出端点级 diff 与受影响的前端调用位置。
- **本地执行**：`mvn -o test -Dtest=ContractConsistencyTest` 可离线跑，输出清单含「已扫描契约文件数 / 端点数 / 不一致项」。
- **覆盖率自校验**：测试输出中明确「目录内契约文件数 = 已校验文件数」，不等即失败（REQ-02）。
- **豁免可见性**：豁免项在报告末尾单列，含原因与过期时间，避免无限期豁免累积。

## 七、数据口径与指标

| 指标 | 口径 | 目标 |
|---|---|---|
| 契约文件覆盖率 | 已校验文件 / 目录内文件 | 100% |
| 端点覆盖数 | 参与校验的端点数 | 随新增自动增长（当前 136） |
| 不一致漏网数 | 上线后才发现的前后端不一致 | **0** |
| CI 门禁生效 | 契约失败是否阻断合流 | 100% 阻断 |
| 离线可跑 | `mvn -o` 下测试通过 | 是 |
| 豁免项数量 | 生效中的豁免条目 | 受控，且均有过期时间 |

## 八、边界场景与异常状态

1. 契约目录中存在示例/废弃文件 → 需白名单排除或标记 `deprecated`，避免误报。
2. 前端动态拼接路径（模板字符串）→ 静态解析可能失败，需约定可解析写法或显式豁免。
3. 同端点多版本（v1/v2）→ 需按版本维度比对，避免交叉误判。
4. 契约 JSON 与代码注解（如 Swagger）双源 → 需明确唯一真源，避免两处漂移。
5. 豁免滥用导致门禁形同虚设 → 豁免必须带过期时间并定期清理（REQ-10）。
6. 离线环境缺依赖导致测试不可跑 → 纯文件解析 + Mockito，不引新依赖（REQ-06）。

## 九、权限与合规

- 契约文件属接口资产，变更需经过评审；不兼容变更需提前通知前端与小程序侧。
- 豁免配置变更需 PR 评审，禁止单人直接合流绕过门禁。
- CI 报告可能包含接口路径与字段，属内部技术资产，不对外公开。

## 十、验收标准（可勾选）

- [ ] 契约文件自动扫描，新增文件无需手动登记（REQ-01）。
- [ ] 测试输出「目录文件数 = 已校验文件数」，不等则失败（REQ-02）。
- [ ] 不一致时输出端点与字段级 diff（REQ-03）。
- [ ] 删除字段/改类型判定为不兼容并阻断（REQ-04）。
- [ ] 新增可选字段/新端点判定为兼容并放行（REQ-05）。
- [ ] `mvn -o` 离线可跑通（REQ-06）。
- [ ] CI 中作为阻断门禁，失败禁止合流（REQ-07）。
- [ ] 契约 JSON 非法时报错定位到文件（REQ-08）。
- [ ] 不兼容变更输出受影响前端调用清单（REQ-09）。
- [ ] 豁免需原因 + 过期时间且在报告可见（REQ-10）。

## 十一、依赖与风险

| 类型 | 说明 | 应对 |
|---|---|---|
| 风险 | 改造后历史不一致集中暴露，一次性 blocking | 先出全量报告，分类处理：真缺陷修复、合理差异走豁免（带过期） |
| 风险 | 硬编码清单改造影响现有测试通过率 | 保留原有断言逻辑，仅替换「清单来源」为自动扫描 |
| 风险 | 前端动态路径无法静态解析 | 约定可解析写法；无法解析的走显式豁免 |
| 风险 | 离线构建要求（不能引新依赖） | 用纯 JSON 解析 + 文件扫描，`mvn -o` 验证通过后再合流 |
| 依赖 | CI 环境（`.github/workflows/ci.yml` 已有） | 新增一个 job/step 即可，MySQL 服务非必需 |
