## 三、F-11 生产基建去 Mock 与资金链路真实化

**目标**：让「能真实收钱、真实分账、真实提现、真实对账」成为默认事实，而非配置选项。这是**上线前置项**，决定业务能否产生真实收入。

### 3.1 任务拆解

| 子项 | 任务 | 涉及模块 / 技术点 | 状态 |
|---|---|---|---|
| F-11.1 | 支付与分账真实化：`RealWechatEscrowServiceImpl` 成为唯一 Bean；回调恒定验签；分账无条件执行；删除演示端点 `/api/pay/mock/{payNo}` 与 `"MOCK"+nanoTime` 假流水号 | `trade/service/PayService`、`SettlementService`、`PayController`、`FundEscrowService` | ✅ 已落地（待验收） |
| F-11.2 | 登录/OSS/ES/MQ/物流/审核去 Mock：删除 8 个 Mock/Local 回退实现，真实实现剥离 `@ConditionalOnProperty` 成为默认 | `user/service`、`file/service`、`search/service`、`trade/service（RocketMqDelay/RealLogistics）`、`item/service` | ✅ 已落地（待验收） |
| F-11.3 | **提现打款真实化**：`WithdrawalService` 审批通过调用真实出款（微信商家转账到零钱），以 `WD{id}` 为幂等单号先查后转，失败回滚（保持冻结）+ 告警；商户配置缺失时硬网关不实际出款 | `trade/service/WithdrawalService`、`FundEscrowService`、`RealWechatEscrowServiceImpl`、商户 API v3 证书 | ✅ 已完成（真实出款接入，幂等先查后转+失败回滚+配置硬网关，提交 83d0275） |
| F-11.4 | **对账自动化与资金告警**：`ReconciliationService.reconcile(day)` 已有比对（已支付订单 vs PAY 流水）；本轮补：差异触发 `SYSTEM_ALERT`（站内+短信）告警工单、定时任务接入 | `trade/service/ReconciliationService`、`schedule/TradeScheduler`、`notify` 告警通道 | ✅ 已完成（差异告警工单 + SYSTEM_ALERT 通道，提交 9b26ecc；待真机验收） |
| F-11.5 | **真机验收**：按 `docs/真机联调验证手册.md` 在真机验证 IM 延迟、支付回流、券领取核销；补充微信支付 v3 回调的**真实签名**联调用例 | `scripts/pay-callback-sim.js`、`scripts/im-loadtest.js` | ⚪ 未开始 |

### 3.2 验收口径
- 真实商户号下单 → `prepay` 返回可用 `prepayParams` → 小程序 `wx.requestPayment` 调起 → 微信异步回调 `/api/pay/notify/v3` → 订单转 `paid`，且**回调验签失败必须被拒**（伪造请求返回 4xx/5xx，不落账）。
- 确认收货后 `SettlementService.onTradeSuccess` 调用 `escrow.profitShare` 成功；分账失败须有告警且不阻断结算单。
- 提现审批通过 → 真实出款成功 → `FundFlow` 与 `Withdrawal` 状态一致；出款失败自动回滚冻结金额。
- 每日对账 `matched=true`，差异 > 0 时产生告警与工单。

### 3.3 风险与对策
- **资金安全为最高优先级**：回调验签、幂等（条件更新 + affected 行网关）、金额校验三者缺一不可；F-11.3 出款必须**先查后转 + 幂等单号**（防重复出款）。
- 无商户号时支付链路不可用（这是移除 Mock 的既定代价）→ 通过环境变量 `IDLEFISH_PAY_*` 注入，接入前用测试商户号联调。

## 四、F-12 可观测性与稳定性体系

**目标**：从「能跑」到「可观测、可定位、可告警」。当前零监控是生产最大盲区。

### 4.1 任务拆解

| 子项 | 任务 | 涉及模块 / 技术点 | 状态 |
|---|---|---|---|
| F-12.1 | **零依赖可观测内核**：`MetricsRegistry`（计数器 + 计时器 + `timed()` 包装）、`ObservabilityFilter`（MDC `traceId` 生成/透传/响应头回写、路由归一化 `{id}` 防维度爆炸、状态码与耗时分布）、`/actuator/health`、`/actuator/metrics` | `common/observability/`（3 个类）、`common/web/WebConfig`（已放行 `/actuator/**`）、`idlefish.observability.enabled` | ✅ 已落地 |
| F-12.2 | **资金链路埋点全覆盖**：已埋 `pay.prepay/refund/notifyV3/paid`、`pay.paid.idempotent_skipped`、`settle.profitshare/settled`；本轮补退款/提现/券核销/回调验签失败埋点（风控冻结随 F-15.1） | `PayService`、`SettlementService`、`WithdrawalService`、`CouponService`、`RiskEngine` | ✅ 已完成（退款/提现/券核销/验签失败埋点，提交 c8facf8；风控冻结留 F-15.1） |
| F-12.3 | **阈值告警**：慢请求（如 P95 > 1s）、错误率、回调验签失败数、对账差异、出款失败，接入 `notify` 告警通道（站内 + 短信 + 企业微信可选） | `common/observability/`、`notify/channel`、`schedule` | ✅ 已完成（AlertEvaluator 阈值引擎 + 冷却去重，提交 c2924bc） |
| F-12.4 | **traceId 全链路透传**：HTTP → 异步（线程池 MDC 传递）→ 出站 HTTP → 调度任务，保证一条链路可端到端串联 | `ObservabilityFilter`、`TraceContext`/`MdcTaskDecorator`/`TraceRestTemplateInterceptor`、`TradeScheduler`/`AlertEvaluator` | ✅ 已完成（TraceContext+MdcTaskDecorator+TraceRestTemplateInterceptor，提交 9589b0d） |
| F-12.5 | **健康检查增强**：`/actuator/health` 增加依赖探活（MySQL/Redis/ES/RocketMQ/OSS），返回 `UP/DEGRADED/DOWN` 与逐项明细，供 K8s readiness/liveness 使用 | `ObservabilityController` + 各 client 探活 | ✅ 已完成（MySQL 真实查询 + 配置/TCP 可达性探测，提交 a5d46b9） |
| F-12.6 | **（条件项）升级 Micrometer/Prometheus**：离线仓库**缺** actuator 与 micrometer-core，**只有联网构建才能引入**。联网后优先用 `spring-boot-starter-actuator` + `micrometer-registry-prometheus`，并把自研 `MetricsRegistry` 适配到 Micrometer 门面 | `pom.xml`（`prod` profile）、`MetricsRegistry` 适配层 | ⚪ 阻塞中（依赖联网环境） |

### 4.2 验收口径
- 任意请求响应头含 `X-Trace-Id`，日志格式含 `[traceId]`，同一链路跨线程/MQ 可串联。
- `/actuator/metrics` 输出路由维度 QPS/耗时/状态码分布；`/actuator/health` 在 MySQL 断开时返回 `DOWN`。
- 人为注入慢接口与异常 → 告警在阈值内触达。

### 4.3 风险
- 指标维度爆炸（URL 中的 id/哈希）→ 已在 Filter 做归一化，扩展时须沿用。
- F-12.6 强依赖联网 `.m2`；保持自研方案与 Micrometer 门面解耦，避免将来二选一冲突。
