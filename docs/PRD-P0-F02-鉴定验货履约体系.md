# PRD｜ITER-F02 鉴定/验货履约体系

| 项 | 内容 |
|---|---|
| 编号 | ITER-F02 |
| 维度 / 优先级 | 功能完善 / **P0** |
| 状态 | 待评审 |
| 建议负责 | 产品负责人（规则与定价）+ 后端负责人（状态机/履约）+ 设计（信任标识） |
| 关联模块 | F-11 物流轨迹（`logisticsTrack`）、F-17 售后维权工单、F-06 评价与信用、F-14.5 BI |

---

## 一、背景与问题

二手交易的第一痛点是**信任**：买家担心假货/货不对板/暗病，卖家难以自证，平台缺乏中立凭据。当前系统已具备售后维权工单（F-17：争议状态机 + 双方举证 + 平台裁决）与物流轨迹（`logisticsTrack`），但**缺少交易前的中立质检凭据**，导致：

- 争议发生时双方各执一词，平台裁决缺乏客观依据，工单处理周期长。
- 高客单价品类（数码 3C、奢侈品、球鞋）转化率受信任瓶颈压制。
- 平台无法对「验货」这一高价值服务进行差异化收费或权益绑定。

**行业趋势**：循环经济与二手质检标准化；头部平台（闲鱼验货宝、转转官方验）已将「先验后买」作为高客单标配。

---

## 二、目标与非目标

**目标（可度量）**
- G1：高客单价品类上线验货后，**争议工单率下降 ≥ 30%**（基线取上线前 30 天同品类工单率）。
- G2：参与验货的商品**成交转化率相对提升 ≥ 15%**（AB 实验口径）。
- G3：验货工单在争议裁决中的**引用率 ≥ 60%**（即裁决能调阅到质检报告）。
- G4：验货服务形成可结算的服务费流水，纳入资金对账（ITER-T02）。

**非目标**
- 本项不自建线下质检中心（接入第三方质检/鉴定机构能力）。
- 不改变现有订单主链路与支付契约；验货作为**可选增值服务**挂载。
- 不承诺 100% 真假如实（明确责任边界与免责说明）。

## 三、目标用户与用户故事

| 角色 | 用户故事 |
|---|---|
| 买家 | 作为买家，我希望下单前能看到中立机构的验货报告，以便放心付款 |
| 卖家 | 作为高价值商品卖家，我希望主动送检以获得「已验」标识，以便更快成交、减少扯皮 |
| 平台客服 | 作为裁决客服，我希望在工单中直接调阅质检报告，以便快速判定责任 |
| 运营 | 作为运营，我希望按品类配置验货准入（如数码 ≥ 2000 元强制推荐），以便控制成本 |

## 四、需求清单（EARS）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| REQ-01 | Ubiquitous | 系统应**始终**将验货服务作为订单的可选属性，未购买验货的订单不得强制阻塞下单 |
| REQ-02 | Event-driven | 当卖家选择「送检」并提交商品时，系统应创建验货单并进入 `待收件` 状态 |
| REQ-03 | Event-driven | 当质检机构回传结果时，系统应将验货单置为 `已验（通过/不通过）` 并生成不可篡改的质检报告快照 |
| REQ-04 | State-driven | 在验货单处于 `验货中` 状态期间，系统应冻结该商品的发货动作，禁止卖家提前发货 |
| REQ-05 | Unwanted | 若验货结果为「不通过」，系统应自动关闭交易、触发退款流程，并向买家推送原因说明 |
| REQ-06 | Event-driven | 当售后工单（F-17）进入举证阶段时，系统应允许客服调阅该订单关联的质检报告 |
| REQ-07 | Event-driven | 当商品完成验货并通过时，系统应在商品详情页与列表页展示「已验」信任标识 |
| REQ-08 | Optional | 若运营配置了品类验货门槛（价格/类目），系统应在发布页提示「建议验货」而非强制 |
| REQ-09 | Unwanted | 若质检机构接口超时或不可用，系统应将验货单置为 `验货异常` 并通知运营，**不得**将订单误判为验货通过 |
| REQ-10 | Event-driven | 当验货服务费产生时，系统应按「分」记账并纳入资金流水与日终对账 |

## 五、流程说明

**主流程（先验后买）**
```
卖家发布（高价值商品）→ [可选] 勾选送检
  → 创建验货单（待收件）→ 物流取件（复用 logisticsTrack）
  → 机构质检 → 回传结果
     ├─ 通过：商品打「已验」标 → 正常交易（买家可放心下单）→ 发货 → 完成
     └─ 不通过：自动关单 → 退款 → 通知买家 + 记录卖家信用
```

**争议场景（事后验货）**
```
买家收货后发起工单（F-17）→ 平台判定需鉴定
  → 生成验货单（争议鉴定）→ 买家寄回 → 机构质检
  → 报告作为裁决依据 → 判定责任方 → 退款或放款
```

**状态机**：`待收件 → 运输中 → 验货中 →（已验通过 | 已验不通过 | 验货异常 | 已取消）`

## 六、交互说明

- **小程序商品详情页**：验货标识（已验/验货中）、报告摘要（成色、功能项、瑕疵图）、「查看完整报告」入口。
- **发布页**：高价值品类出现「建议验货」提示与费用说明（REQ-08，非强制）。
- **订单详情**：验货进度条（复用物流时间轴样式），明确展示当前状态与预计完成时间。
- **PC 后台（新增验货管理菜单）**：验货单列表（筛选：状态/品类/机构）、报告调阅、异常单人工处理、服务费对账。
- **工单详情（F-17）**：「调阅质检报告」按钮（REQ-06）。

## 七、数据口径与指标

| 指标 | 口径 | 目标 |
|---|---|---|
| 验货渗透率 | 已验订单 / 高价值品类订单 | 上线 3 个月内 ≥ 20% |
| 争议工单率降幅 | （上线前工单率 − 上线后）/ 上线前 | ≥ 30% |
| 转化率提升 | 已验商品转化率 vs 对照组 | ≥ 15%（AB） |
| 验货时效 | 创建验货单 → 出报告中位时长 | ≤ 48h（品类可配） |
| 报告调阅率 | 引用报告的工单 / 需鉴定工单 | ≥ 60% |
| 金额口径 | 服务费、退款金额统一「分」 | 强制 |

## 八、边界场景与异常状态

1. 验货期间买家取消订单 / 卖家撤回送检。
2. 质检机构判定「无法判定」（如改装机、配件缺失）→ 归入 `验货异常`，转人工。
3. 验货通过后买家仍以「与报告不符」发起争议 → 以报告快照为裁决基准，平台承担兜底责任需明确。
4. 商品在质检机构处损坏/丢失 → 需明确赔付主体（机构/平台/物流）与保险机制。
5. 同一商品重复送检、报告版本覆盖（保留历史版本，不可篡改）。
6. 验货异常超时未处理 → 自动转人工工单并告警。

## 九、权限与合规

- 质检报告属**证据级数据**，需只读快照存储，禁止事后编辑；访问需留痕（谁在何时调阅）。
- 报告含商品图片与个人寄件信息，需按个保法脱敏展示（隐藏收寄件人完整地址/电话）。
- 验货服务协议与免责条款需法务评审；明确「验货不等同于真伪保证」的责任边界。
- PC 验货管理菜单纳入 RBAC（角色管理），仅质检运营与客服主管可调阅。

## 十、验收标准（可勾选）

- [ ] 高价值商品发布页出现「建议验货」提示且**非强制**（REQ-01/08）。
- [ ] 送检后订单发货动作被冻结，直至验货完成（REQ-04）。
- [ ] 验货通过生成报告快照，商品页展示「已验」标识（REQ-07）。
- [ ] 验货不通过自动关单退款，并推送原因（REQ-05）。
- [ ] 机构接口超时时置为「验货异常」，未被误判为通过（REQ-09）。
- [ ] F-17 工单可一键调阅质检报告，且调阅留痕（REQ-06）。
- [ ] 服务费按「分」入账并进入日终对账（REQ-10）。
- [ ] PC 验货管理菜单受 RBAC 控制，无权限角色不可见。
- [ ] 报告与个人寄件信息展示已脱敏。

## 十一、依赖与风险

| 类型 | 说明 | 应对 |
|---|---|---|
| 依赖 | 第三方质检/鉴定机构接口、物流取件能力（`logisticsTrack`） | 先接 1 家机构做 MVP，抽象机构适配层 |
| 依赖 | F-17 工单举证阶段扩展点 | 复用现有状态机，新增「调阅报告」动作 |
| 风险 | 验货成本高于服务费收入，长期亏损 | 按品类/客单价差异化定价，先在高客单试点 |
| 风险 | 机构判定争议引发平台责任 | 协议与免责条款前置法务评审 + 报告快照留痕 |
| 风险 | 验货时效过长拖累转化 | 设定 SLA 与超时自动转人工，超时则退款保障买家 |
